THE BASELINE SCOPE RULE 

When coming up with an idea for an AI-assisted game, it is crucial to pick a    
game that could theoretically be built without AI in a single weekend. 

1 

WHY THIS CONSTRAINT? 

It ensures the core gameplay loop is achievable before introducing    
complex AI layers. If the game can't exist without AI, it can't be    
validated, iterated, or shipped reliably. 

2 

THE TEST 

Ask yourself: could two developers build a rough but playable version    
of this game in 48 hours? If yes, it's scopeable for AI augmentation.  
![][image15]  
"ONE AGENT, ONE WOW" 

Mastering the "One Agent, One Wow" rule allows developers to    
realistically scope AI features that can actually ship within a set    
deadline. 

ONE EXCEPTIONAL TASK 

Each agent should be responsible for doing one thing    
extraordinarily well \- not everything adequately. Focus guarantees    
functional success. 

THE COST OF OVER-SCOPING 

Assigning too many responsibilities to a single agent leads to    
broken logic and unpredictable outputs that cannot ship. 

YOUR TURN

Name it. Describe what the player does in one sentence.   
Now identify the one AI-driven moment that makes it worth playing. 

That moment is your 'One Agent, One Wow.'   
Design the whole Technical Strategy section around making that    
moment work \- before building anything else.  
THE THREE NEW PILLARS OF AI GDD

PILLAR 1: THE AI DEV PIPELINE 

A comprehensive AI-centric GDD explicitly maps  how the AI dev pipeline will function \- from raw  text data flowing through an AI node, translated via  JSON scripts, directly into the game engine  (Unity/Unreal). 

THE AI DEV PIPELINE  
WHY IT MATTERS 

This ensures a clear understanding of exactly how  the agents will talk to the game engine. Without  this map, integration breaks silently and  

unpredictably. 

PILLAR 2: TECHNICAL   
REQUIREMENTS &   
CONSTRAINTS 

An AI GDD must rigorously define all technical requirements and operational constraints \- including API Limits, Context Window Size, and Processing Latency.   
THE RISK OF SKIPPING THIS 

Failing to map these constraints early results in systems that cannot be sustained in a live production environment. Constraints are a feature, not a limitation. 

TECHNICAL REQUIREMENTS & CONSTRAINTS

PILLAR 3: TOKEN BUDGETS & PROJECTIONS 

Unlike theoretical documentation, a modern GDD tackles the financial reality of LLMs by projecting token budgets and generation costs before a single line of code is written. 

TOKEN BUDGETS & PROJECTIONS  
STAYING COMMERCIALLY   
VIABLE 

Establishing these projections early ensures that the multi-agent system remains commercially viable and avoids runaway API bills at scale.

THE DEV CREW

ASSIGNING AGENT ROLES 

Defining the "dev crew" involves systematically mapping and assigning specific roles to the    
agent team within the GDD. 

DEDICATED & SPECIALIZED 

Every piece of generation requires a dedicated, specialized agent rather than a    
generalized model. Specialization is the foundation of a reliable pipeline. 

MAPPED IN THE GDD 

Agent roles are not improvised at runtime \- they are formally documented in the GDD with    
defined inputs, outputs, and scope of responsibility. 

MIRRORING A REAL STUDIO 

The dev crew structure mirrors a real game studio hierarchy, maximizing efficiency and    
accountability across the full production pipeline.

DEMO \#1: USING AN AGENT TEAM TO "STRESS TEST" A GDD

FINDING LOGIC GAPS 

A live demo showcases how to use an Agent team to proactively find logic    
gaps in the design document before a single line of code is written. 

SYNTHETIC AUDIENCE 

The AI acts as a synthetic audience \- evaluating the viability of game    
mechanics and surfacing conflicting rules that would cause    
breakdowns at runtime. 

ERROR REPORTING 

The agent returns a structured error report highlighting exactly where    
the GDD logic conflicts, giving designers clear, actionable revision    
targets. 

NO CODE REQUIRED 

This validation happens entirely at the document level, catching    
critical design flaws at the cheapest possible stage of development.

GENERATING ASSET   
SPECIFICATIONS 

After finding logic gaps, the agent team generates structured asset   
specifications from the GDD descriptions: 

{   
"asset\_type": "character\_sprite",   
"style": "pixel art, top-down",   
"palette": "dark fantasy (blacks, deep reds)",   
"dimensions": "32x32 tile",   
"animation\_states": \["idle", "walk", "attack", "death"\]   
} 

STRUCTURED OUTPUT 

These specs are precise enough to hand to an artist or use as a brief for   
asset creation. 

COHERENCE CHECK 

If the agent can't produce a structured spec from your GDD description,   
the description is too vague to build from.  
CASE STUDY \#2: VAN BUREN BLACK ISLE STUDIOS' UNRELEASED FALLOUT 3 (2003) 

WHAT IT IS 

A complete AAA game design document for a full Fallout RPG \- cancelled when Interplay shut down Black Isle in December 2003\. When the game was cancelled, Black Isle released the full GDD. It is the only publicly available production-scale GDD for a major AAA franchise. You can read every page.   
WHY IT MATTERS FOR THIS SESSION 

The GDD covers: world systems, character stats, faction logic, quest structure, technical constraints, engine requirements, scope estimates, and team responsibilities. Van Buren is what your GDD is reaching toward. Not in scope \- in rigor.
