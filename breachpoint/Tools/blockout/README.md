# Tools/blockout — the BR_Arena01 generator

`Content/Data/arena_manifest.json` is the source of truth. `Content/Maps/BR_Arena01.umap`
is its **projection**. This folder is the only sanctioned way to turn one into the other.

> CLAUDE.md law 7: *blockouts … are generated by committed scripts, never hand-placed.*
> If you find yourself dragging a cube in the level editor to fix the arena, stop — the fix
> belongs in the manifest, and the manifest belongs to BP13 / arena-architect.

Doctrine: `.claude/skills/ue-editor`.

## Files

| file | what it is | needs the editor? |
| --- | --- | --- |
| `arena_plan.py` | reads + **validates** the manifest, derives the ordered build plan, prints/serialises it | **no** — plain CPython 3.9+, stdlib only |
| `build_arena.py` | dumb executor: takes that plan and places actors in the level | yes — imports `unreal` |
| `blockout_profile.json` | construction constants (deck thickness, crate sizes, eye height, class paths) | no |
| `build-arena.ps1` | the wrapper: engine resolution, R21 editor guard, logging, ladder exit codes | only when actually building |

The split is the point. Every *decision* — what gets built, where, why, and whether the
manifest is even legal — happens in `arena_plan.py`, which anyone can run and review with no
engine installed and no editor free. `build_arena.py` makes no geometric decisions at all.

## How to run it

**Validate the manifest / see the whole plan (safe any time, launches nothing):**

```powershell
Tools\blockout\build-arena.ps1 -PlanOnly
# or, straight to python:
python Tools\blockout\arena_plan.py --verbose
```

**Build the map (needs a free editor and an LFS lock on the .umap):**

```powershell
Tools\blockout\build-arena.ps1
Tools\blockout\build-arena.ps1 -DryRun        # opens nothing, validates under the editor
Tools\blockout\build-arena.ps1 -Strict        # refuse any element whose extents were inferred
```

Raw headless form, if you are not using the wrapper:

```
<ENGINE_ROOT>\Engine\Binaries\Win64\UnrealEditor-Cmd.exe ^
    <REPO>\Breachpoint.uproject ^
    -run=pythonscript -script="<REPO>\Tools\blockout\build_arena.py" ^
    -stdout -unattended -nosplash -nop4 -NoLiveCoding
```

Script switches travel in `BR_BLOCKOUT_ARGS` (the wrapper sets it) because argument passing
into `-run=pythonscript` differs between launch shapes; `sys.argv` is also honoured.

Prerequisites: `Tools/env.local` with `ENGINE_ROOT` (same file the rest of the ladder uses —
there is no hardcoded engine path anywhere here), the **Python Editor Script Plugin** enabled
in `Breachpoint.uproject`, and `git lfs`.

## What determinism means here (and what it does not)

Re-runnability is the requirement: the `.umap` is a derived artifact, so running the
generator twice on the same manifest must produce the same arena. Four mechanisms:

1. **Clear-and-rebuild by tag.** Every actor this script creates is tagged
   `BlockoutGenerated` (`blockout_profile.json → map.generated_tag`). The first thing a run
   does after opening the level is destroy every actor carrying that tag. A re-run is a
   rebuild, never an append — so it cannot accumulate duplicates, and deleting a landmark
   from the manifest actually deletes it from the map.
2. **Deterministic naming.** Every label is derived from manifest ids/names through
   `slug()` plus a zero-padded index (`BR_Spawn_SP5`, `BR_LM_The_Gantry_02`). No counters
   that depend on editor state, no timestamps, no GUIDs, no randomness anywhere in the
   toolchain.
3. **Fixed emission order.** Sections emit in a fixed order (floor → walls → landmarks →
   cover → spawns → power-weapon node → nav → lights), and within a section in manifest
   array order — `json.load` preserves document order — then in footprint text order.
   Nothing iterates an unordered set. Every float is rounded before it enters the plan.
4. **A digest to check it with.** `plan.digest` is sha256 over the canonical element list
   (labels, tags, transforms, sizes). Two runs agree **iff** the digest agrees. It is
   printed by every run and stored in the build report.

Verified on 1 Aug 2026: three `arena_plan.py` runs under different `PYTHONHASHSEED` values
produced byte-identical plan JSON, digest `edcd17cc…`.

**What is NOT claimed:** the `.umap` will *not* be byte-identical between runs — Unreal
reserialises object GUIDs and package metadata on every save. Determinism here means *the
actor set is identical*, which is the property that matters and the one the digest proves.
Judge a rebuild by its digest and by the build report, not by the binary diff.

## Failing loudly

`arena_plan.py` refuses to produce a buildable plan when the manifest breaks the ticket's
Kickoff numbers, and `build_arena.py` refuses to touch the level if any error is present.
There is deliberately **no override flag for validation errors** — a silently-built bad
arena is worse than no arena.

The four Kickoff thresholds are constants in `arena_plan.py`
(`KICKOFF_MIN_SPAWNS`, `KICKOFF_MIN_SPAWN_SPACING_M`, `KICKOFF_MAX_SIGHTLINE_M`,
`KICKOFF_ROCKET_LANDMARK_REQUIRED`) and are deliberately **not** readable from
`blockout_profile.json`: a gate that a data file can weaken is not a gate.

Error codes that block a build: `SPAWN_COUNT`, `SPAWN_SPACING`, `SPAWN_DUP_ID`,
`SPAWN_OUT_OF_BOUNDS`, `SPAWN_NO_LOC`, `SIGHTLINE_CAP`, `SIGHTLINE_UNDECLARED`,
`SIGHTLINE_OPEN_PAIR`, `ROCKET_LANDMARK_MISSING`, `ROCKET_NODE_UNBUILDABLE`,
`LANDMARK_NO_FOOTPRINT`, `COVER_HEIGHT_CLASS`, `COVER_NO_LOC`.
Warnings (recorded, printed, do not block): `DECK_UNCONNECTED`, `GRAPPLE_POINTS_ABSENT`,
`LANDING_NOTE_COUNT`, `COVER_DUPLICATES_LANDMARK`, `INFERRED_GEOMETRY`,
`ROCKET_NAME_INDIRECT`, `SPAWN_NO_FACING`, `SPAWN_NO_HINTS`.

The sightline check is static: it raises both endpoints to `eye_height_m` and slab-tests the
segment against every solid AABB the manifest names. It is a rung-1 algebraic check on
spawn-to-spawn lines only — exactly the class of claim the manifest's own `doubts[]` says is
insufficient. It does **not** sweep oblique lines and it is not a substitute for the
walkthrough.

## When it will not build

As landed (manifest sha `268b04e6…`), the plan **fails validation** on
`ROCKET_NODE_UNBUILDABLE`: `The Core` names the Rocket Launcher pad but declares itself
*solid* across `x[16,24] y[16,24] z[0,9]`, and the manifest carries no `rocket_node` point.
There is nowhere to put `ABRPowerWeaponSpawner` that is not inside a solid volume, and the
manifest's own `landing_note` forbids adjusting geometry here ("any adjustment here is a
silent drift … must instead go back through review as a new revision"). So the generator
stops. **Fix the manifest, never this script.** The manifest needs a structured
`rocket_node: {x, y, z}` reconciled with the Core's solidity.

## Known gaps for the manifest owner (BP13 / arena-architect)

- **Landmark geometry lives in prose.** Footprints are parsed out of the free-text `purpose`
  field with a regex (`x[16,24] y[16,24], z[0,9]`), and z-heights are inferred from phrases
  like *"at z=4"*, *"full-height"*, *"stair connectors … to the Gantry"*. Every inferred
  element says so in its `derivation`, and `-Strict` refuses to build them. A v3 manifest
  should carry structured `footprint` objects so nothing is parsed out of English.
- **`height_class` carries no dimensions**, so crate sizes come from
  `blockout_profile.json`. Those are build constants, not gameplay tuning — but the arena
  would be better described if the manifest owned them.
- **No `grapple_points[]`.** The ticket asks for grapple markup and ">= 2 grapple points per
  upper position"; the manifest names none, so this generator emits none. It will not invent
  a gameplay affordance.

## After a successful build

Exit code 0 means *actors placed, level saved*. That is the generated rung and nothing more.
Nav build, reachability, and the four `doubts[]` in the manifest's `landing_note` are a
rung-3 walkthrough with screenshots (BP07 step 4, owner: verifier). A commandlet run has no
viewport, so screenshots come from an interactive editor, not from this script.

Each run writes `Saved/Blockout/blockout-<stamp>-<verdict>.json` — plan digest, manifest
sha256, every element with its derivation, every finding, and what was cleared. Attach it to
the ticket Log alongside the screenshots; it is the spot-audit table BP07's "Done when"
asks for.
