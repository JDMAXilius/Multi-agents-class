# Tools/gen_input — the Content/Input generator

`Tools/gen_input/input_profile.json` is the source of truth. The eleven `IA_*` assets,
`DA_InputConfig` and `IMC_Default`'s new key bindings are its **projection**. This folder is
the only sanctioned way to turn one into the other.

> CLAUDE.md law 7: *input assets are generated by committed scripts, never hand-placed.*
> If you find yourself retyping a key in the Input Mapping Context editor, stop — the rebind
> belongs in `input_profile.json`, and a re-run puts it in the asset.

Contract:
`docs/contracts/data-and-assets.md`. Doctrine: `.claude/skills/ue-editor`. Precedent and
structure: `Tools/blockout` (BP07) — same two-half split, same wrapper, same exit codes.

## Files

| file | what it is | needs the editor? |
| --- | --- | --- |
| `input_plan.py` | reads + **validates** the profile, derives the plan, prints/serialises it | **no** — plain CPython 3.9+, stdlib only |
| `build_input.py` | executor + the asserts only a live asset can answer | yes — imports `unreal` |
| `input_profile.json` | the eleven actions, their tags/value types/triggers, and the key bindings | no |
| `selftest_no_editor.py` | drives `build_input.py` against a **fake** `unreal` — 8 cases | **no** |
| `build-input.ps1` | the wrapper: engine resolution, plugin check, R21 editor guard, logging, ladder exit codes | only when actually generating |

The split is the point. Every *decision* — which actions exist, which tags they carry, which
triggers are legal, which keys — happens in `input_plan.py`, which anyone can run and review
with no engine installed and no editor free. `build_input.py` decides nothing; it applies the
plan and then audits what it wrote.

## How to run it

**Validate the profile / see the whole plan (safe any time, launches nothing):**

```powershell
Tools\gen_input\build-input.ps1 -PlanOnly
# or straight to python:
python Tools\gen_input\input_plan.py --verbose
```

**Test the generator's logic without an editor (also launches nothing):**

```powershell
Tools\gen_input\build-input.ps1 -SelfTest
python Tools\gen_input\selftest_no_editor.py
```

**Generate the assets (needs a free editor):**

```powershell
Tools\gen_input\build-input.ps1
Tools\gen_input\build-input.ps1 -DryRun       # audits under the editor, writes nothing
Tools\gen_input\build-input.ps1 -AllowDrift   # repair a hand-edit without failing the run
```

Raw headless form, if you are not using the wrapper:

```
<ENGINE_ROOT>\Engine\Binaries\Win64\UnrealEditor-Cmd.exe ^
    <REPO>\Breachpoint.uproject ^
    -run=pythonscript -script="<REPO>\Tools\gen_input\build_input.py" ^
    -stdout -unattended -nosplash -nop4 -NoLiveCoding
```

Script switches travel in `BR_GENINPUT_ARGS` (the wrapper sets it) because argument passing
into `-run=pythonscript` differs between launch shapes; `sys.argv` is also honoured.

**Prerequisites:** `Tools/env.local` with `ENGINE_ROOT` (the same file the rest of the ladder
uses — no hardcoded engine path anywhere here), `git lfs`, and the **Python Editor Script
Plugin enabled in `Breachpoint.uproject`**. That last one is *not currently enabled* — see
"Known gaps" at the bottom. The wrapper checks it and blocks with the exact JSON to add,
rather than letting `-run=pythonscript` fail as an unknown commandlet.

## What it produces

Eleven `UInputAction` assets in `/Game/Input/Actions` — `IA_Move`, `IA_Look`, `IA_Jump`
already exist and are updated in place; `IA_Crouch`, `IA_Sprint`, `IA_Fire`, `IA_Reload`,
`IA_Swap`, `IA_Grenade`, `IA_Melee`, `IA_Grapple` are created. `IA_Move` and `IA_Look` are
**Axis2D**; every other one is **Digital (bool)**.

`DA_InputConfig`, a `UBRInputConfig` instance, with four native rows (Move/Look/Jump/Crouch)
and seven ability rows (Sprint/Fire/Reload/Swap/Grenade/Melee/Grapple), each pairing a **soft**
`TSoftObjectPtr<UInputAction>` with its `InputTag.*`.

`IMC_Default` gains ten key mappings for the eight new actions. It is **extended, never
replaced**: see "Idempotency" below.

`IA_MouseLook` is a template asset, is not one of the eleven, and is never read or written.

## The trigger contract, and how it is *asserted*

The seven ability actions must use the **default (empty) trigger set or an explicit `Down`
trigger**, never `Pressed`. A `Pressed` trigger ends the action one frame after the press and
delivers `Completed` *while the key is still held* — a release that never happened. That
silently breaks `WaitInputRelease`, every `WhileHeld` ability (sprint, held fire) and every
toggle, and it breaks them in a way that looks like an ability bug rather than an asset bug.
The C++ side of the same contract is documented on `UBRInputConfig::AbilityInputActions` and
`UBRInputComponent::BindAbilityActions`.

Applying it would not be enough — a hand-edit in the editor would undo it silently. It is
asserted in **four** places:

1. **The profile cannot legalise it.** `CONTRACT_ABILITY_TRIGGERS_ALLOWED` and
   `CONTRACT_BANNED_TRIGGER` are constants in `input_plan.py` and are deliberately *not*
   readable from `input_profile.json`. A profile naming `Pressed` fails validation and no
   asset is written. (Same rule as BP07's kickoff thresholds: a gate a data file can weaken
   is not a gate.)
2. **The live asset is audited before anything is written.** Every asset already on disk has
   its triggers read and compared. A banned — or merely *unrecognised* — trigger on an
   ability action is reported as `CONTRACT_VIOLATION_ON_DISK`, naming the asset and the
   trigger class. An unknown trigger class is treated as a violation, not given the benefit
   of the doubt: "we cannot tell what this does" is not "this is fine".
3. **The repair does not hide the edit.** The generator repairs the asset (the profile is the
   source of truth) *and then fails the run*, exit 1, unless `--allow-drift` is passed. The
   repair is done; the non-zero exit exists so the hand-edit is **seen**. Re-run for a clean
   pass.
4. **A post-write pass re-asserts it** independently of the diff that drove the write, plus
   the real `UBRInputConfig::IsDataValid` via the editor's validator subsystem. A violation
   that survives the write fails the run and says the assets are not trustworthy.

## Idempotency — how a re-run stays a no-op

Running twice must change nothing. Four mechanisms, and the self-test proves the first three:

1. **Load, never recreate.** An asset that exists is loaded and updated in place, so
   `IA_Move`/`IA_Look`/`IA_Jump` keep every template setting this generator does not manage
   (description, consume-input flags, player-mappable settings).
2. **Diff before write.** Nothing is set unless the live value already differs, and nothing
   is saved unless something was set. A second run reports every package as `in_sync` and
   calls `save_loaded_asset` zero times — which also means zero pointless LFS churn on a
   binary. `selftest_no_editor.py` asserts `saves == []` on the second run.
3. **Per-action clear-and-rebuild in the IMC.** For an action the profile marks
   `generator_owns_mappings`, the update is `unmap_all_keys_from_action` then `map_key` — a
   scoped clear-and-rebuild, the same shape as BP07's clear-by-tag. Nothing is ever appended
   blindly, so a re-run cannot accumulate duplicate mappings, and deleting a key from the
   profile actually deletes it from the asset. Actions the profile does **not** own (the
   template's Move/Look/Jump, with their negate/swizzle modifiers and pad bindings) are never
   read for equality and never written.
4. **Deterministic derivation.** Package paths come from action names; the two config lists
   are emitted in the *contract* tag order, not profile order, so re-ordering the JSON cannot
   re-order the asset. No counters, timestamps, GUIDs or randomness anywhere.
   `plan["digest"]` is sha256 over the action set, both config lists and the mappings —
   printed by every run. Verified 1 Aug 2026: four `input_plan.py` runs under different
   `PYTHONHASHSEED` values produced digest `019f2418…`.

**What is NOT claimed:** the `.uasset` bytes will not be identical between runs that write —
Unreal reserialises package metadata and object GUIDs on every save. Determinism here means
*the asset set and its authored properties are identical*, which is what the digest and the
in-sync report cover. Judge a re-run by "saved: none", not by a binary diff.

## Failing loudly

There is deliberately **no override flag for validation errors**. A silently-generated bad
control scheme is worse than no control scheme: it presents as an ability bug, in a match,
weeks later.

Plan-side error codes (no asset is written if any appear): `ACTION_COUNT`, `ACTION_NAME_SHAPE`,
`ACTION_DUPLICATE`, `ACTION_LIST`, `TAG_MISSING`, `TAG_UNEXPECTED`, `ROW_NO_TAG`,
`ROW_TAG_FAMILY`, `TAG_DUPLICATE_IN_LIST`, `TAG_DUPLICATE_ACROSS_LISTS`, `VALUE_TYPE_UNKNOWN`,
`VALUE_TYPE_CONTRACT`, `TRIGGER_UNKNOWN`, **`TRIGGER_PRESSED_BANNED`**, `TRIGGER_NOT_ALLOWED`,
`KEYS_MISSING`, `KEY_NAME_SHAPE`, `KEY_COLLISION`, `PACKAGE_PATH`,
`PACKAGE_OUT_OF_OWNER_PATH`, `CONFIG_CLASS`.
Warnings (recorded, do not block): `TRIGGER_PRESSED_NATIVE`, `KEYS_NOT_APPLIED`.

Editor-side: `CONTRACT_VIOLATION_ON_DISK`, `DRIFT_VALUE_TYPE`, `DRIFT_TRIGGERS`,
`DRIFT_CONFIG_ROWS`, `DRIFT_IMC_MAPPINGS`, `KEY_COLLISION_LIVE`, `VERIFY_*`, `ISDATAVALID`,
`VALIDATION_UNAVAILABLE`. Plus hard refusals (exit 1) for: an unregistered `InputTag.*`
(meaning this editor build does not carry `Core/BRGameplayTags.h`), a missing
`unreal.BRInputConfig` (the module is not compiled into this editor), a missing `IMC_Default`
(this generator extends the template's context, it will not invent one), an unrewritable
pre-existing binary that is not lfs-locked, and any Python-binding name this script cannot
resolve.

Each run writes `Saved/InputGen/input-<stamp>-<verdict>.json` — plan digest, profile sha256,
every finding, what was created/saved/in-sync, the mtime of every file written, and the
verbatim output of `IsDataValid`. Attach it to the ticket Log.

## Rungs — what a green run does and does not mean

Exit 0 means: the assets exist, they read back exactly as `input_profile.json` describes
them, every file this run claims to have written is newer than the run itself, and
`UBRInputConfig::IsDataValid` accepted the config. That is the **generated** rung.

It does **not** mean a key does anything. Nothing here proves the mapping context is added at
runtime, that `ABRPlayerController` has `DA_InputConfig` assigned, or that a tag reaches the
ASC. That is a PIE smoke (BP01 step 5, owner: verifier) — and PIE is not multiplayer.

`selftest_no_editor.py` is a rung below even that: it drives the generator against a **fake**
`unreal` module and proves the generator's *decisions* — the eight creations, the zero-write
re-run, the drift catch, the collision refusal. It proves nothing about the engine.

## Known gaps (each needs an owner outside this folder)

- **`PythonScriptPlugin` / `EditorScriptingUtilities` are not enabled** in
  `Breachpoint.uproject`. Nothing in `Tools/` can run under the editor until they are, and
  `Tools/blockout` (BP07) has the same prerequisite. `Breachpoint.uproject` is outside this
  packet's `owner_path`, so this is filed as a contract_gap rather than fixed here.
- **No gamepad bindings.** The packet's defaults are keyboard/mouse; a pad layout is a design
  call nobody has made. Adding one is keys in `input_profile.json` plus a re-run.
- **No per-mapping modifiers or triggers.** The eight new mappings are plain digital keys and
  need none. `build_input.py` does not author mapping-level modifiers at all — a known limit,
  not a silent one.
- **`Config/DefaultGameplayTags.ini` does not exist** (noted in BP01's Log). Native tags
  self-register, so the generator's tag assert passes today; if that ever changes, the assert
  is what will tell you.
