# Tools/render_weapons — the weapon silhouette generator

> **This is a spike. The render path has never been run.** No editor was opened to write any
> of it. `render_plan.py` and `selftest_no_editor.py` are proven — they are arithmetic and a
> CSV. `render_weapons.py` is a best-effort first pass written from the UE 5.8 docs, and
> **the first run is expected to fail and to correct §3.3 of the plan document**, not to
> succeed silently. If it exits 0 on the first try, be suspicious before you are pleased.

`Tools/render_weapons/render_plan.py` is the source of truth. The PNGs in `out/` and the
textures in `/Game/UI/Icons/Weapons` are its **projection**.

> CLAUDE.md law 7: *assets are generated by committed scripts, never hand-placed.*
> If you find yourself in Photoshop nudging an icon, stop — the fix is a number in
> `render_plan.py` and a re-run (`WEAPON-RENDER-PLAN.md` §5.3).

Plan: `docs/ui/WEAPON-RENDER-PLAN.md` — read it first; this README does not repeat it.
Rulings: R37 (committed plan + receipt), R21/R29/R36 (editor vs. project lock).
Doctrine: `.claude/skills/ue-editor`. Structure and idiom: `Tools/gen_input` (BP01).

## Files

| file | what it is | needs the editor? |
| --- | --- | --- |
| `render_plan.py` | **the committed table** + validation + the framing math | **no** — plain CPython 3.9+, stdlib only |
| `render_weapons.py` | executor: load, override, frame, capture, post-process, receipt | yes — imports `unreal` |
| `selftest_no_editor.py` | 14 cases over the plan, the refusals and the framing math | **no** |
| `render-weapons.ps1` | wrapper: engine resolution, plugin check, **R21 editor guard**, logging | only when rendering |
| `out/*.png` | the rendered projections (and the raw `*_ss4x.png` from each run) | no |
| `receipts/*.md` | R37 receipts, one per run, written as the run proceeds | no |

The split is the point. Every *decision* — which meshes, which output names, the shared
scale, the orientation corrections — happens in `render_plan.py`, which anyone can run and
review with no engine installed and no editor free.

**Departure from `WEAPON-RENDER-PLAN.md` §4.1, recorded:** the plan called for the table in
`weapon_render_profile.json` and skipped a `*_plan.py`. It is inverted here — one Python file
holding the table *and* its validation — because the framing values are unverified guesses and
JSON cannot carry the warning next to the number. Move the table back to JSON when the values
are real.

## How to run it

**Validate the plan / see every framing number (safe any time, launches nothing):**

```powershell
Tools\render_weapons\render-weapons.ps1 -PlanOnly
python Tools\render_weapons\render_plan.py --verbose
python Tools\render_weapons\render_plan.py --json Saved\WeaponRender\plan.json
```

**Self-test, also no editor:**

```powershell
Tools\render_weapons\render-weapons.ps1 -SelfTest
python Tools\render_weapons\selftest_no_editor.py
```

**Render (needs a free editor, no build in flight):**

```powershell
Tools\render_weapons\render-weapons.ps1
Tools\render_weapons\render-weapons.ps1 -DryRun    # loads and frames under the editor, writes nothing
```

Raw headless form — **this bypasses the R21 editor guard, so check by hand first**:

```
<ENGINE_ROOT>\Engine\Binaries\Win64\UnrealEditor-Cmd.exe ^
    <REPO>\Breachpoint.uproject ^
    -run=pythonscript -script="<REPO>\Tools\render_weapons\render_weapons.py" ^
    -stdout -unattended -nosplash -nop4 -NoLiveCoding
```

Switches travel in `BR_RENDERWPN_ARGS` (the wrapper sets it), matching `BR_GENINPUT_ARGS` and
`BR_BLOCKOUT_ARGS` — argument passing into `-run=pythonscript` differs between launch shapes
and the env var is the one that always survives. `ENGINE_ROOT` comes from `Tools/env.local`;
there is no hardcoded engine path in this folder.

**Before you launch:** no editor window open (the wrapper enforces it via the shared
`Get-BRLiveEditorProcesses`), **and no builder live** — R36 widened R29.3 so that anything
taking the project lock counts, and this commandlet takes it without being a build. If the
session is stopped mid-run the commandlet keeps running and keeps the lock (R21): kill the
process tree, do not dispatch over it.

## What the first run is expected to reveal

It exists to answer questions the repo cannot. Work the **SPIKE CHECKLIST**
(`docs/ui/WEAPON-RENDER-PLAN.md` §11) with the receipt and the raw `out/*_ss4x.png` in front
of you. The short version:

1. **The authoring axes.** Which local axis is the barrel on each mesh, and where the pivot
   sits. All three rows ship at the identity guess `yaw_deg=0, roll_deg=0, flip_x=false`
   precisely because identity is the guess that is *easiest to see being wrong*: a weapon
   rendered nose-on collapses to a stub, and one on a strange pivot sits off-centre at the
   right size. Both are legible in one glance at a 768×256 frame.
2. **Whether the flat-white override reads.** `M_FlatCol` was named in §3.3 as the obvious
   candidate and explicitly marked unverified — nobody has read its parameters. A grey or
   shaded render means the output contract (§2.2: every pixel `#FFFFFF`, shape in alpha) is
   not being met and §3.3 needs rewriting, not tuning.
3. **Whether TAA is actually off**, and whether the ShowFlags names in `render_weapons.py`
   exist at all. The receipt logs a `SHOWFLAG_UNSETTABLE` warning per flag it could not set.
4. **Whether a `-run=pythonscript` commandlet has a world to spawn into.** If it does not,
   the whole capture strategy is wrong and the fix is a different mechanism, not a parameter.

## Feeding the answers back

The loop is deliberately one-directional: **observations become numbers in `render_plan.py`,
and nothing else ever changes.**

1. Read the receipt (`receipts/render-<stamp>.md`) and open the raw `out/<name>_ss4x.png`.
2. Edit the `WEAPONS` table in `render_plan.py`: set `yaw_deg` / `roll_deg` / `flip_x` to what
   the frame showed. **Put the receipt stamp in the comment on the line you change** — §4.2
   requires every non-zero orientation value to be justified, and "justified" means citing the
   run that determined it, not asserting it looks right.
3. Delete the `UNVERIFIED GUESS` banner over the table, and delete the
   `the_framing_values_are_still_guesses` tripwire case in `selftest_no_editor.py` — it fails
   on purpose once the values are real, so the stale warning cannot outlive the guess.
4. If the *mechanism* was wrong (not the numbers), correct **§3.3 of the plan document** in
   the same commit. The plan is the artifact that outlives this folder.
5. Re-run `-SelfTest`, then `-PlanOnly`, then the render. Commit the PNG, the `.uasset` and
   the receipt **together** — R37: a receipt not committed with the asset is not a receipt.

## What is deliberately NOT implemented in the spike

Named so nobody reads a green run as more than it is:

- **The 2 px minimum-feature test** (§7.2) — the check is automatable, the fix is not. The
  receipt records `NOT IMPLEMENTED IN THE SPIKE` per weapon rather than a passing verdict.
- **Hole detection and the ≤2 reduction** (§7.3). `hole_keep` is honoured by nothing today;
  a non-empty value raises a warning saying so.
- **Texture import** into `/Game/UI/Icons/Weapons` with the §2.4 settings. The spike stops at
  the PNG, which is the reviewable artifact; importing is the next rung and it writes into
  BP10's owner path (law 5 — that packet, or a `contract_gap`).
- **Any consumer.** There is no icon field on the weapon row, no column in `DT_Weapons.csv`
  and none on `UBRVM_Combat` (§9.3). Rendering the PNGs puts nothing on screen, and saying
  otherwise is the exact defect law 6 exists to catch.

## Failing loudly

There is no override flag for validation errors. Plan-side codes (nothing renders if any
appear): `MESH_PATH_DRIFT`, `ROW_MISSING`, `ROW_UNKNOWN`, `ROW_DUPLICATE`, `MESH_PATH_SHAPE`,
`OUT_NAME_SHAPE`, `OUT_NAME_ROW_MISMATCH`, `OUT_NAME_DUPLICATE`, `OUT_SIZE_DEPARTURE`,
`ANGLE_TYPE`, `FLIP_TYPE`, `SCALE_OVERRIDE_SHAPE`, `SCALE_OVERRIDE_UNJUSTIFIED`,
`HOLE_KEEP_TOO_MANY`, `PACKAGE_OUT_OF_OWNER_PATH`, `CAMERA_ROLL`, `FILL_FRACTION`,
`SUPERSAMPLE`. Warnings: `ORIENTATION_CORRECTION`, `HOLE_KEEP_NOT_IMPLEMENTED`.

`MESH_PATH_DRIFT` is the one that matters. If the icon can be rendered from a mesh other than
the one the game equips, the icon can drift from the weapon — the failure mode of a drawing,
reintroduced with more steps. `selftest_no_editor.py` proves it fires.

Editor-side: `MESH_NOT_FOUND`, `MATERIAL_NOT_PARAMETERISED`, `SHOWFLAG_UNSETTABLE`,
`VERTICAL_OVERFLOW`, `RENDER_NO_OUTPUT`, `POSTPROCESS_UNAVAILABLE`, `ACTOR_NOT_DESTROYED`,
plus hard refusals for an unresolvable `unreal` binding, an interactive editor session
(R21), and a missing unlit override material.

Every run writes `receipts/render-<stamp>.md` and `Saved/WeaponRender/render-<stamp>-<verdict>.json`
— **as it goes, refusals included**. A receipt reconstructed afterwards is not a receipt.

## Rungs

`-SelfTest` and `-PlanOnly`: a Python table and some arithmetic, no engine. They prove the
plan is self-consistent and that the framing math is right *given correct bounds*. They cannot
tell you the orientation guesses are wrong.

A green render run means: three PNGs exist, they match the plan, and the meshes they came from
are the meshes `DT_Weapons.csv` equips. It does **not** mean the icons are right, legible, or
on screen. §8.3's identity test — show the three at final size to someone who knows the three
weapons, no labels — is the real bar, and no script scores it.
