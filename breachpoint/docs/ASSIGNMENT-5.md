# Assignment #5 — Autonomous Agency (ELVTR S07)

**Project:** BREACHPOINT — a 4v4 arena FPS in Unreal Engine 5.8, pure native C++, built by a
crew of agents against a ticket board.
**The agent under assessment:** *The Architect* (`Tools/architect/`, ticket
`docs/tickets/TICKET_BP15_ARCHITECT.md`) — a layer that decides **what the crew builds next**,
then hands that decision to the existing builder → critic → verifier pipeline.

**The honest one-paragraph summary.** The architect ran. It scanned the codebase, scored all 44
architectural units with printed terms and zero API calls, wrote an authorisation record, and
dispatched a builder packet. **The packet produced no gameplay code.** It stopped at the
project's owner-path law because the unit it had selected had no inputs on disk — undeclared
gameplay tags, missing data columns, missing tuning fields. Separately, an adversarial review of
the architect itself found six defects, one of which invalidated the selection: the scorer's
"blocker count" term was counting *already-finished* units as work waiting on the candidate. When
that was fixed, **the pick changed**, and the ticket's most-quoted success claim had to be
retracted. This document reports all of that, because the alternative — writing up a feature that
did not ship — is precisely the failure mode this project's honesty rules exist to prevent.

---

## Vocabulary (one line each, for a reader who does not know the codebase)

| Term | Meaning here |
|---|---|
| **Unit** | One numbered architectural component (a C++ class or a header of related structs), e.g. `BRGA_WeaponFire`. The full list of 44 is declared in `BREACHPOINT-ARCHITECTURE.md` §3, which is the project's *manifest*. |
| **GAS** | Unreal's Gameplay Ability System. Actions are *abilities*; stat changes go through *GameplayEffects*; visuals go through *GameplayCues*. |
| **Gameplay tag** | A hierarchical string identifier registered in C++ (`Ability.Weapon.Fire`). Nothing can reference a tag the code has not declared. |
| **DataTable / `DT_*.csv`** | Tuning numbers live in CSV, not in code. C++ reads them through row structs in `Source/Breachpoint/Data/BRDataRows.h`. |
| **Ticket / packet** | A unit of work with an `owner_path` — the one folder its agent is allowed to write in. Blocked? File a `contract_gap` and **stop**; never edit someone else's folder to unblock yourself. |
| **Rung** | The evidence ladder. Rung 1 = it compiles (all three build targets). Rung 2 = automated specs pass. Rung 4 = it works over a real network. "Compiles" is never allowed to stand in for "works". |
| **BUILT / STUB / MISSING** | The scanner's classification of each unit against what is actually on disk. |

## Q1 — What feature did the agent build?

### The short answer: no gameplay feature was built.

Nothing under `Source/Breachpoint/` was generated by the architect's builder packet. No `.h`, no
`.cpp`, no diff. The step-4 entry in the ticket Log records this in the plainest terms available:
*"STOPPED at law 5 before writing a line of C++, and separately BLOCKED on the rungs. Zero
Done-when boxes added."*

What the run actually produced is three things. They are real, they are in the repository, and
none of them is a game feature.

### 1. The selection layer itself (`Tools/architect/`, 1,013 lines of Python across three files)

| File | What it is |
|---|---|
| `architect.py` | `--scan` (perception) · `--rank` (scoring) · `--blackboard` (authorisation) · `--all` |
| `build_state.py` | Regenerates `docs/BUILD-STATE.md` from the two JSON outputs + `git log`; every fact copied from an input, never restated |
| `test_selfcheck.py` | Red-then-green harness: drives the real parser over one faithful manifest and four corrupted ones |
| `state/perception.json` | The disk scan: 43 in-slice + 1 Phase-2 reserved = 44 units; **BUILT 34 · STUB 0 · MISSING 10** |
| `state/ranking.json` | All 44 units scored, every term stored, not just the total |
| `blackboard/2026-08-01-BRSpotterSubsystem.md` | The authorisation record for the currently-selected unit |

The perception pass is not a toy. Its self-check refuses to run if the architecture document
disagrees with itself, and it carries one finding that is worth more than the code: the project's
seven generic GameplayEffect classes are declared in **one** header
(`AbilitySystem/Effects/BRGameplayEffects.h`), so a scanner that counts *files* is wrong before it
starts. That premise error had been recorded twice in project documentation as "six classes across
17 files". It is now counted by class declaration and asserted against the header at scan time, so
it cannot drift silently again.

### 2. One real unblock, in the game code: four gameplay tags

The one thing that reached `Source/` as a consequence of this run is four tag declarations in
`Source/Breachpoint/Core/BRGameplayTags.h`/`.cpp`:

```
Ability.Weapon.Fire
GameplayCue.Weapon.AR.Fire
GameplayCue.Weapon.Magnum.Fire
GameplayCue.Weapon.Rocket.Fire
```

Verified today, read-only: **34 `UE_DECLARE_GAMEPLAY_TAG_EXTERN` / 34 `UE_DEFINE_GAMEPLAY_TAG`**,
balanced. This matters beyond the four lines because `Content/Data/DT_Weapons.csv` had been
shipping a `FireCueTag` column naming all three cue tags since 29 July — **data referencing symbols
the code had never declared, through every gate, with a verifier PASS**, because the verifier
checked the CSV's *schema* and not whether the symbols on the other end existed. Declaring the tags
closes today's instance. It does not close the class of bug; a validator for tag-valued CSV columns
is filed as a proposal and is **not built**.

Two honesty caveats on this item:
- It landed under a **BP03** claim (the weapons ticket), not under the architect's own packet —
  because the architect's packet was not allowed to write there.
- **It has never been compiled.** Rung 1 is blocked: a UE editor session is live on this machine
  and the project's ruling R29.3 forbids overlapping an editor session with a build.

### 3. One validator: `test_selfcheck.py`

Built because the ticket's acceptance criterion says the scanner "exits nonzero on any mismatch",
and a mechanism that has only ever been observed *passing* is not evidence of enforcement. Run
live for this writeup:

```
faithful copy                 ACCEPT    0      ok
header/table disagree         REJECT    2      ok
a unit silently dropped       REJECT    2      ok
budget no longer reaches 44   REJECT    2      ok
§3's shape changed entirely   REJECT    2      ok
All 5 cases behaved.
```

Driving the four *rejecting* cases found a real defect in `architect.py` that the passing case
never would have: `Path.relative_to` raises on a non-subpath, so a cosmetic log-formatting helper
was load-bearing and crashed the control case. That is the argument for red-then-green in one
sentence.

### Why the selected unit produced no code

The architect selected `BRGA_WeaponFire` (the weapon fire ability), wrote its blackboard, and
dispatched the builder. The builder opened the unit's specification and stopped, filing three
`contract_gap`s. All three verified by execution, and re-verified read-only for this document:

| # | Missing input | Evidence checked today | Status |
|---|---|---|---|
| 1 | `Ability.Weapon.Fire` + three `GameplayCue.Weapon.*.Fire` tags undeclared | now present, 34/34 balanced | **RESOLVED** (see above) |
| 2 | `FBRWeaponRow` has no trace range and no spread | `grep -E "Range\|Spread"` over `BRDataRows.h` returns **one** hit, inside an unrelated comment at line 350. `CT_Combat.csv` holds 11 curve rows, none of them range or spread | **OPEN** |
| 3 | `DT_Weapons.csv` has no `AbilitySet` column | header is 16 columns: `Name,DisplayName,FireMode,DamageDelivery,DamagePerShot,RPM,MagSize,ReserveMags,ReloadTime_s,HeadshotMult,ProjectileSpeed,SplashRadius_m,SplashDamage,EquipTime_s,MeshSoftPath,FireCueTag` | **OPEN** |

Gap 2 is the hard stop. A hitscan ability with no range and no spread would have to invent both,
and a literal gameplay number written next to a gameplay noun is a direct violation of this
project's law 3 (*data is not code*) — the builder would be writing the exact thing the critic
exists to reject. Gap 3 means that even a perfect implementation could never be **granted** to a
player, because equipping a weapon grants its ability set and there is no column to read one from.

**The result I would report to a stakeholder:** the pipeline behaved correctly. It stopped at a
boundary instead of editing three other owners' files to unblock itself. That is the behaviour the
owner-path law exists to produce, and it was proven by execution rather than asserted.

**The result I would not let a stakeholder walk away believing:** stopping is not the same as being
right to stop. One of the three gaps was filed against the wrong owner — the builder read a
file-level comment at the top of `BRGameplayTags.h` that had been written *before* the ruling that
superseded it, and pre-refused itself on a rule that no longer existed. A `contract_gap` filed
against a lifted rule is indistinguishable, at the moment of filing, from a real one. **Obedience is
not correctness**, and a board that only measures "did the agent stop?" cannot tell the difference.

## Q2 — Why did it pick that one?

This is the part the assignment is actually about, so here is the whole mechanism, and then the
uncomfortable fact that **the pick changed**.

### The scoring function

```
score = depth + blockers + tier + state
```

Four terms, all printed, defined in `Tools/architect/architect.py`:

| Term | What it measures | Where the number comes from |
|---|---|---|
| **depth** | Dependency depth — how deep in the dependency graph the unit sits | `max(ticket_depth, include_depth)`: distance from the roots of the hand-declared ticket DAG (`TICKET_DEPS`, 16 tickets, each edge taken from that ticket's own "gated by" line), unioned with the depth of real `#include` edges parsed out of `Source/` |
| **blockers** | How many units transitively wait on this one | union of (units that `#include` it, transitively) and (units belonging to tickets that transitively depend on its ticket) |
| **tier** | GDD tier — is this in the vertical slice, or reserved for Phase 2? | `slice = 0`, `phase2 = -100` |
| **state** | Current state on disk | `MISSING = 100` · `STUB = 50` · `BUILT = -1000` |

Two of those magnitudes look strange and are deliberate. **`state` and `tier` are gates, not
nudges.** A BUILT unit scores −1000 so it can never outrank an unbuilt one no matter what else it
accumulates; a Phase-2 unit takes −100 so a permanently-missing placeholder can never be selected
to build. The first draft used `state = 2/1/0` and was swamped — see the defects below.

**Ties break on lowest ticket number, then unit name.** Literally:

```python
rows.sort(key=lambda r: (-r["total"], int(re.sub(r"\D", "", r["ticket"]) or 99), r["unit"]))
```

That is a total order over the unit set with no model input and no dictionary-ordering dependence.

### The claim that no LLM chooses the unit, and how it is provable

Every number above is produced by deterministic Python. The proof is not rhetorical:

| Claim | How it is checked | Result |
|---|---|---|
| Zero API calls | `architect.py` imports only `argparse, json, re, sys, datetime, pathlib`. `build_state.py` adds `subprocess`, used only to shell out to `git`. **No network import exists in either file** — verified read-only today | holds |
| Same input, same order | `perception.json`, `ranking.json` and the full run log are byte-identical across two runs | holds |
| No model in the tie-break | the sort key above | holds |
| The self-check rejects what it claims to | `test_selfcheck.py` 5/5, run live for this document | holds |

The model is only ever handed a unit that the score has already picked. A ranking that came out of
a model is a ranking nobody can audit — that is the design premise, and it survived an adversarial
review that was actively trying to break it.

It survived with **one serious asterisk**, which is in Q3: two of the four terms are computed by
parsing `Source/`, and `Source/` is what the model writes. The *scorer* is not an LLM, but two of
its *inputs* are downstream of one.

### The pick, version 1 — `BRGA_WeaponFire`, total 106

| unit | ticket | state | depth | blockers | tier | state | **TOTAL** |
|---|---|---|---|---|---|---|---|
| **BRGA_WeaponFire** | BP03 | MISSING | 2 | **4** | 0 | 100 | **106** |
| BRGA_WeaponUtility | BP03 | MISSING | 2 | 4 | 0 | 100 | 106 |
| BRSpotterSubsystem | BP11 | MISSING | 4 | 0 | 0 | 100 | 104 |
| BRGA_Grenade | BP05 | MISSING | 2 | 1 | 0 | 100 | 103 |

`BRGA_WeaponUtility` tied at 106 and lost on unit name (same ticket number, later name) — the
tie-break rule firing exactly as specified.

This result was, at the time, reported as the strongest evidence the ticket could produce. The
project's own handoff note said the next human move was *"restart BP03 step 2 — the fire path"*,
and a scorer with no knowledge of that note had landed on the same unit. That was written up as
independent corroboration.

### The pick, version 2 — `BRSpotterSubsystem`, total 104

An adversarial review of the architect (a `critic` agent in REFUTER mode, running the real code
inside throwaway repository copies) asked whether any *absent* term was producing a confidently
wrong ranking. It found one, and it was the whole margin.

**The defect (`F6a`): `blockers` counted units that were already BUILT as "waiting on this one."**
The function walked downstream tickets and added *every* unit belonging to them, regardless of
whether that unit had already been finished. Asked who exactly was recorded as waiting on the
selected unit, the answer was:

| waiter | state | ticket |
|---|---|---|
| `BRActivatableWidget` | **BUILT** | BP10 |
| `BRHUDLayout` | **BUILT** | BP10 |
| `BRUIManagerSubsystem` | **BUILT** | BP10 |
| `BRViewModels` | **BUILT** | BP10 |

All four were finished UI widgets. **Nothing was waiting on `BRGA_WeaponFire`.** Its blocker term
was 4/4 fictional, and 4 was exactly the margin that put it first.

The fix is one line in `architect.py` (`rank()`):

```python
waiters = {w for w in waiters if by_unit.get(w, {}).get("state") != "BUILT"}
```

The current ranking, read verbatim out of `Tools/architect/state/ranking.json`:

| # | unit | ticket | state | depth | blockers | tier | state | **TOTAL** |
|---|---|---|---|---|---|---|---|---|
| **1** | **BRSpotterSubsystem** | BP11 | MISSING | **4** | 0 | 0 | 100 | **104** |
| 2 | BRGA_Grenade | BP05 | MISSING | 2 | 1 | 0 | 100 | 103 |
| 3 | BRGA_Melee | BP05 | MISSING | 2 | 1 | 0 | 100 | 103 |
| 4 | BRGA_Grapple | BP06 | MISSING | 3 | 0 | 0 | 100 | 103 |
| 5 | BRGA_WeaponFire | BP03 | MISSING | 2 | **0** | 0 | 100 | **102** |
| 6 | BRGA_WeaponUtility | BP03 | MISSING | 2 | 0 | 0 | 100 | 102 |
| 7 | BRBotDeterminismSpec | BP00 | MISSING | 0 | 0 | 0 | 100 | 100 |
| 8 | BRCombatSpec | BP00 | MISSING | 0 | 0 | 0 | 100 | 100 |
| 9 | BRShieldSpec | BP00 | MISSING | 0 | 0 | 0 | 100 | 100 |
| 10 | BRGameLiftLifecycle | BP11 | MISSING | 4 | 0 | **-100** | 100 | **4** |

Row 10 is the tier gate working as designed: a unit reserved for Phase 2 and expected to be MISSING
for the entire slice is pushed to the bottom of the selectable set, so it can never be chosen as
"the next thing to build".

**The consequence for the write-up, stated plainly:** the agreement between the scorer and the
human board was **an artifact of the defect**. Correct the term and the scorer picks
`BRSpotterSubsystem`, which the human board is not proposing at all. That claim is retracted in
full — see Q3.

## Q3 — What did you change before accepting it into the game?

Nothing was accepted into the game — no generated code exists to accept. So the honest form of this
question is: *what did review change about the agent, and what did review change about what we were
willing to claim?* Both lists are long, and the second one matters more.

### The retraction

The ticket's most-repeated line was that the scorer *"independently landed on the fire path … the
strongest evidence this ticket can produce that the scoring is measuring something real."*

**It does not survive `F6a`.** The entire 4-point blocker score that produced the agreement was
four already-built widgets. The number that flattered the mechanism was produced by the
mechanism's own bug. It is now recorded in the ticket Log as a retraction, at length, rather than
quietly corrected — because a coincidence cited as corroboration is exactly the kind of claim that
propagates into a slide deck and never gets re-checked.

### Four wrong picks, in order, each caught by a different mechanism

| # | The score picked | Why it was wrong | The fix |
|---|---|---|---|
| 1 | `BRCharacter` — **already BUILT** | `state` used 2/1/0 while `blockers` reached 35, so state was swamped. A *what to build next* scorer selected something already built | `state` became a gate: MISSING 100 · STUB 50 · BUILT −1000 |
| 2 | `BRGA_Grapple` — **gated two tickets deep** | units were attributed to tickets by *folder*, but tickets cut across folders: all six abilities live in `AbilitySystem/`, so all six were attributed to BP02. `BRGA_Grapple` is BP06's — gated behind BP05, gated behind BP02. The score was ranking a unit that could not legally be started, and it was the single hardest unit in the codebase | a `UNIT_TICKET` override map, each entry justified by the ticket whose **title** names the unit's subject |
| 3 | `BRGA_WeaponFire` — **106 was inflated** | `F6a`, above | filter waiters to non-BUILT units |
| 4 | `BRSpotterSubsystem` — **currently selected, and it is the least startable unit on the board** | `F6b`, unfixed — see the next section | not fixed; it is a design decision, not a builder's call |

### Defects found in the agent by adversarial review

The `critic` agent asked five questions the ticket specifies, plus a sixth it does not. **All six
answered "yes."** Every answer was an executed input producing a wrong outcome, run against
byte-identical copies of the real code in throwaway repositories. Three were fixed.

**Fixed — `F5` (high): the architect could overwrite any Markdown file in the repository.**
`blackboard()` built its output path by interpolating `ranked[0]["unit"]` — re-read from
`state/ranking.json` on disk — straight into a filename, with no re-validation. A single crafted
string in that JSON file made the tool write outside its own directory: one probe wrote into
`Source/Breachpoint/AbilitySystem/`, contradicting the tool's own docstring (*"Nothing under
`Source/` is ever opened for writing here"*); a second probe **replaced this very ticket's 495-line
Log with a blackboard**. The same input would have destroyed `CLAUDE.md`, the contracts, or the
architecture manifest the scanner parses. The project's tool-call hook could not have caught it —
the hook inspects Edit/Write tool calls and is blind to a Python process writing through `pathlib`.
Fixed with `safe_unit_name()`, which requires a bare `BR*` identifier; the probe payload now exits
1 with a refusal.

*A detail worth keeping:* on Windows the naive traversal payload **fails** for an unrelated
platform reason (Win32 strips trailing dots, so the path component is misread). One extra character
restores it. A failed exploit attempt on one platform is not evidence the exploit is impossible.

**Fixed — `F4` (high): the state classifier was wrong in both directions.** It called things BUILT
that contain no code, and called finished work a STUB.

| probe `.cpp` | what it contains | old verdict |
|---|---|---|
| empty constructor + empty `ActivateAbility()` | zero statements | **BUILT** |
| one block comment, four prose lines | zero code | **BUILT** |
| three functions wrapped in `#if 0 … #endif` | nothing the compiler sees | **BUILT** |

The inverse was live in the repository at the time: `docs/BUILD-STATE.md` — the project's state of
record — listed `BRDataRows` as a **STUB** and offered it as the tenth thing to build.
`BRDataRows.h` is 889 lines, 35 KB, eight `USTRUCT`s, and its own header comment declares it *"the
ONE header for every `DT_` DataTable row struct in the project."* It has no `.cpp` **by design** —
plain structs need no translation unit. Two more finished units were misreported the same way.

Both errors have one root: the classifier measured *the presence and line count of a `.cpp`*, which
is a fact about the C++ build model, not about whether a unit is implemented. Fixed two ways: count
statements by semicolons outside comments, dead preprocessor blocks and includes; and parse the
**expected form** out of the manifest, which had the answer all along — §3 writes `BRDataRows.h`,
not `BRDataRows.h/.cpp`. The tally moved from **BUILT 31 · STUB 3 · MISSING 10** to
**BUILT 34 · STUB 0 · MISSING 10**.

The compound version of this defect nearly happened for real: `state` is the 1100-point term, and
it is computed from files the *model* writes. Had the step-4 builder written a header plus a
boilerplate `.cpp` before filing its `contract_gap`, its unit would have flipped MISSING (100) →
BUILT (−1000) — a swing of 1100 points, permanently out of the queue — and `BUILD-STATE.md` would
have reported the weapon fire path as **built**. It stopped before writing a file, which is the
only reason that unit is still rankable.

**Fixed — `F6a` (high):** the blocker term, above.

### The change to the process, not the code

Three of the corrections here were made by the agent's own critic, not by a human noticing. The
one that a human had to make was the retraction — deciding that a number which agreed with our
expectations was *more* suspect for agreeing, not less. That is the durable lesson from this
assignment, and it cost nothing to apply: re-run the scorer with the defect fixed and see whether
the agreement survives. It did not.

## What is still wrong

Stated without softening, because a deliverable that lists only its fixes is the same failure as a
deliverable that claims a feature shipped.

**The corrected score now picks the *least* startable unit on the board.** `BRSpotterSubsystem` is
BP11 — gated by BP08, gated by BP02 and BP04 — and it wins on **depth 4 alone**. That is `F6b`:
`score = depth + blockers + tier + state` **adds** depth, and depth is *distance from the roots of
the dependency graph*, i.e. how many tickets must finish first. Adding it means the more
prerequisites a unit has, the higher it scores — a sign error for a "what to build next" scorer.
The evidence is in the generated state file itself: the three test specs have `depth 0`, are
startable today, and rank 7–9; while the same file reports rung 2 as BLOCKED *because those three
specs do not exist*. **Not fixed** — the four terms are the ticket's specification and inverting
one is a design decision for the project owner, not a change an implementing agent should make on
its own initiative.

**Open findings, all filed with reproductions, none fixed:**

- **`F1` (high)** — a unit the score did **not** pick can be landed, and `docs/BUILD-STATE.md` will
  attest it as BUILT. Nothing anywhere compares a landing to an authorisation; the owner-path gate
  checks *folders*, and the selected unit's folder contains six different abilities, so any of them
  passes. Worse, the next scan then reclassifies the unauthorised unit as BUILT and drops it out of
  the queue — the trace erases itself.
- **`F2` (medium)** — the acceptance criterion "the blackboard predates the generated source" rests
  entirely on file modification time, which is resettable. The blackboard filename is
  day-granular, so a second run on the same day silently overwrites the first authorisation. Two
  sessions on one day cannot both be recorded.
- **`F3` (high)** — two of the four terms (`depth`, `blockers`) are parsed out of `Source/`, which
  is what the model writes: the scorer is in a feedback loop with its own output. Adding **one
  `#include` line naming a header that does not exist** moved a unit +27 points and to #1. The
  include parser checks that the name is a declared unit; it never checks that the header exists,
  so a line that cannot compile still moves the ranking.
- **`F6b`** — the depth sign, above.
- **`F7` (medium)** — the red-then-green harness exercises only the manifest parser. The
  classifier, the ranker and the blackboard writer have **zero** test cases — and `F4` and `F5`
  were both found in exactly that gap.

**And the rungs.** Nothing in this write-up has been compiled. Rung 1 (three build targets) and
rung 2 (specs) are both BLOCKED: a UE editor session is live and ruling R29.3 forbids overlapping
it with a build; `Source/Breachpoint/Tests/` still holds only a `.gitkeep`. The four gameplay tags
that were declared are declaration-only with no logic — which is an argument about risk, not
evidence. On this project's ladder, *compiles ≠ works*, and this work has not even reached
*compiles*.
