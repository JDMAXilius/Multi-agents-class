## The gap

Those six cues write `User.Team_Color` into their Niagara system every time they fire. The
systems **do not declare it**, and a Niagara USER parameter that the system does not declare
is dropped with no warning, no log and no colour. The code has looked correct this whole time.

Measured across every `NS_*` in the project — only FOUR declare a colour parameter at all:

```
NS_Grenade_Explosion   User.Team_Color     (wired)
NS_Grenade_Trail       User.Team_Color     (wired 28 Aug)
NS_DeathCubes          User.BodyColor      (nothing references this asset)
NS_JumpPad             User.Color          (nothing references this asset)
```

The rest — including **every smoke system** — declare no colour parameter of any kind, so
there is no `TintParameter=` override that rescues them. `NS_WeaponFire_MuzzleFlash_Rifle`
declares only Direction / SmokePuffTexture / Trigger; `NS_WeaponFire_Tracer` only
ImpactPositions / MuzzlePosition / Trigger; `NS_ImpactConcrete` only impact geometry.

## Why this is a contract_gap and not a task

Fixing it means opening each Niagara system and authoring a colour USER parameter wired into
the emitter's colour output. There is no sanctioned scripted path to that:

- **MCP has no Niagara toolset.** 23 toolsets are registered; none touches Niagara.
  (`list_toolsets`, checked 28 Aug — the count differs from the skill's remembered list,
  which is why it was re-checked rather than trusted.)
- **The engine exposes no Python API for it either.** `NiagaraEditor/Public` ships only the
  script-UPGRADE helpers (`UpgradeNiagaraScriptResults`); there is no user-parameter
  authoring entry point to call from `-run=pythonscript`.
- **Law 7** says an asset is generated by a committed script, never hand-placed, and the
  founder does not do manual editor setup.

So the honest options are a founder call, not an implementation detail:

1. **Author the parameter by hand, once, in the Niagara editor** for the systems worth it
   (muzzle flash and impact read most on screen). Explicitly a law-7 exception, logged here.
2. **Replace the template FX** with systems authored to expose `User.Team_Color`.
3. **Accept it.** Bodies, explosion and grenade trail carry the team read; weapon FX stay
   neutral. Cheapest, and arguably correct — Halo does not tint bullet impacts either.
4. **Route the tint through materials instead** — needs a per-component material override,
   which Niagara only offers through a declared `User.<Material>` parameter. Same wall.

Recommendation: **3**, with **1** for muzzle flash only if the founder wants it. The tint
call in those six cues costs nothing and starts working the day a system declares the name.

## Log

**28 Aug 2026** — Audit written (`Tools/bn/80_team_audit.py`) and run against the live editor.
Found and fixed two real defects on the way: the grenade trail was never tinted though its
system declares the parameter, and the team material config was `UPROPERTY(Config)` only,
which is loaded from the ini but inspectable from nowhere — no details panel, no property
query, so "did the config land" had no answer from inside the editor. Both now carry
`EditDefaultsOnly` beside `Config`, matching `TintParameter`'s precedent.

The audit itself had two bugs worth naming, both of the class it exists to prevent:
`get_properties` fails the WHOLE call when one requested name is absent (Tracer has no Sound,
Death has no Effect), which reported six healthy classes as unreadable; and the intersect that
fixed it was case-sensitive while the lister answers camelCase, which turned the mesh slot
check into a SILENT SKIP — the four materials still printed OK while the pairing that can be
invisibly swapped went unchecked. Both fixed; the skip now prints FAIL and files a finding.

**28 Aug 2026, second pass** — Founder: "grenade explosion effect should have team colour
relevant." It was reported APPLIED by the audit and was still drawing neutral, which exposed
the limit of what the audit had actually proven.

The audit proved the ASSET declares a colour parameter. That is not the same claim as A
COLOUR REACHES IT, and the blast was failing on the second one: `MulticastExplosion` hands the
cue `this` — the projectile — and `ResolveTeamTint` opened with `Cast<APawn>(Target)`, which is
null for a projectile every time. No PlayerState, no colour, no tint. Silent, because a tint
that resolves to "no answer" is indistinguishable from FFA, and a comment in the same file
asserted this was "the one cue where it currently draws".

Fixed in the SHARED resolver rather than at the explosion's call site: any future cue handled
on a non-pawn (a decal, a dropped weapon, any prop) had the identical bug waiting, and one
guard in the resolver is a smaller diff than a guard per caller. `ResolveEffectOwner` is the
target when it is a pawn, otherwise the target's instigator — and it is split out public
precisely so it can be pinned headless, which the viewer half cannot be.

`BNEffectOwnerSpec` now holds three rows: the projectile resolves to its thrower (the row that
would have caught this), a pawn target stays its own owner even with a misleading instigator
(the fallback must not become an override), and an ownerless actor answers null rather than
guessing.

NOTE for the founder: your OWN blast still draws neutral. That is the pre-existing cue rule —
"your own fire keeps the look it has always had" — not an oversight; teammates read Ally blue
and enemies Threat red. Say the word if you want your own grenade tinted too; it is one line,
but it contradicts a rule the other cues follow, so it is not mine to flip.

Still unproven without eyes-on: that the parameter reaches the visible output. Evidence is
strong — it is a declared user parameter, `UserParamBinding` is in the package name table, and
its default is `(1,1,1,1)`, the canonical white tint identity — but a screenshot of PIE is the
only thing that closes it, and CaptureViewport returns the EDITOR viewport, not PIE.
