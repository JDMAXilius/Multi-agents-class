# Motion & interaction — the front end and HUD in UE 5.8 / UMG / CommonUI terms

**What this is.** The buildable translation of `docs/ui/MOTION-MEASURED.md` into UMG animation
tracks, CommonUI input, and the C++ that triggers them. Every timing here is either **[M]
measured** (cited to `MOTION-MEASURED.md`) or **[P] proposal** (invented by me, labelled, with the
reason it was chosen). Nothing is presented as measured that is not.

**Authority.** `CLAUDE.md` law 4 (no gameplay Tick) and R18/R26 (`docs/DESIGN-RULINGS.md`) are the
binding constraints, and they produce the single architectural rule this whole document turns on:

> **The WBP holds the animation track. C++ holds the trigger. There is no third place.**
>
> A `UWidgetAnimation` is layout-adjacent authored data — R18's Tier-4 UMG allowance covers it, and
> `ui-presentation` §8 names "animation" explicitly. But *deciding when it plays* is a decision, and
> R26 condition 2 says the WBP's graph has zero nodes. So every animation is bound into C++ with
> `UPROPERTY(Transient, meta = (BindWidgetAnim)) TObjectPtr<UWidgetAnimation> Anim_X;` and started
> by a C++ `PlayAnimation(...)` call from a delegate handler. Never from a graph. Never from Tick.

**Related.** `ue5-ui-architecture` (CommonUI/MVVM mechanics — and note its own standing
UNVERIFIED-DRAFT warning about CommonUI API drift across 5.x; that warning applies to §5 below).
`ui-presentation` §3 (colour semantics), §4 (fidelity tiers), §8 (what crosses the Figma boundary),
§10 (what a UI packet must never do). `docs/ui/SCREEN-BUILD-SPEC.md` §7 (interactions the structure
proves).

**Rung honesty.** Nothing in this file has been run against a build. It is a spec at rung 0. §9 is
how it climbs.

## 1. The house curve in UE — what UMG can and cannot express

### 1.1 The token

```
Motion.Ease.Standard = cubic-bezier(0.45, 0.15, 0.10, 1.00)
```

[M] `MOTION-MEASURED.md` "the single most important result": fitted across five independent
scale/translate series in three assets, mean RMSE **0.066**, versus 0.140 for `ease-out`, 0.191 for
`ease-in-out`, 0.201 for linear. Everything below uses it unless the row says otherwise.

Its shape matters and is why the reflex `ease-in-out` is *measurably wrong*: a soft start
(slope 0.333), then a **hard flat landing** (slope 0.000). It arrives and stops. It does not
decelerate symmetrically.

### 1.2 What a UMG animation track actually is

A `UWidgetAnimation` is a `UMovieSceneSequence`. Each animated property is a MovieScene float/2D
track whose keys are `FRichCurveKey`. Per-key interpolation modes are Constant, Linear, and Cubic;
cubic keys carry `ArriveTangent` / `LeaveTangent`, and — this is the load-bearing detail —
optionally `ArriveTangentWeight` / `LeaveTangentWeight` when `TangentWeightMode` is set to
`RCTWM_WeightedBoth` ("Weighted Tangents → Both" in the curve editor's key context menu).

**A two-key cubic segment with weighted tangents *is* a cubic Bézier.** So the curve is exactly
expressible. But:

> **An UNWEIGHTED cubic key cannot express this curve.** UE's default tangent weight is 1/3 of the
> segment, which pins the Bézier's x-controls to `x1 = 0.3333` and `x2 = 0.6667`. Our curve needs
> `x1 = 0.45` and `x2 = 0.10`. `x2 = 0.10` is nowhere near 2/3 — the flat landing is precisely the
> part the default weighting destroys. **If weighted tangents are not enabled on both keys, you are
> shipping a different curve and it will look like every other engine's default ease.** This is the
> single most likely way this spec gets built wrong.

### 1.3 The numbers to type into the curve editor

For a track normalised to a 0→1 value change over a segment of duration `D`:

| key | field | value | derivation |
|---|---|---|---|
| start (t=0, v=0) | Interp | Cubic, Weighted Both | — |
| | LeaveTangent (slope) | **0.3333** | `y1 / x1 = 0.15 / 0.45` |
| | LeaveTangentWeight | **0.4743 × L** | `|(x1, y1)| = √(0.45² + 0.15²)` |
| end (t=D, v=1) | Interp | Cubic, Weighted Both | — |
| | ArriveTangent (slope) | **0.0000** | `(1 − y2) / (1 − x2) = 0 / 0.9` — the flat landing |
| | ArriveTangentWeight | **0.9000 × L** | `|(x2 − 1, y2 − 1)| = |(−0.90, 0)|` |

`L` is the segment's diagonal length in the curve editor's own (time, value) units. The **ratios
0.4743 and 0.9000 are exact**; the unit scaling of `L` is the one thing here that needs a single
confirming pass in the editor before it is trusted (§9, rung 2).

### 1.4 Two authoring routes, and which to prefer

**Route A — script-generated tracks (preferred).** Tier 3 of `BREACHPOINT-AUTHORING-MATRIX.md`:
generated by a committed script, not hand-placed. A commandlet/Python pass writes the animation's
keys from a table of named transitions. The generator is text, greppable and diffable; the `.uasset`
becomes an output rather than a hand-authored artifact. This also sidesteps §1.3's `L` question
entirely by writing 20 **linear** keys sampled from the Bézier at 16.5 ms — visually
indistinguishable at 60 Hz and completely deterministic.

Bézier sampler (the only maths anyone needs, ~6 lines):

```
# cubic-bezier(0.45, 0.15, 0.10, 1.00): solve x(t)=alpha for t by Newton, then return y(t)
B  = lambda a, b, t: 3*(1-t)**2*t*a + 3*(1-t)*t*t*b + t**3          # a,b are the two controls
dB = lambda a, b, t: 3*(1-t)**2*a + 6*(1-t)*t*(b-a) + 3*t*t*(1-b)
def ease_standard(alpha, x1=0.45, y1=0.15, x2=0.10, y2=1.00):
    t = alpha
    for _ in range(6): t -= (B(x1, x2, t) - alpha) / max(dB(x1, x2, t), 1e-6)
    return B(y1, y2, min(max(t, 0.0), 1.0))
```

**Route B — hand-authored in the curve editor.** Two keys, weighted tangents, §1.3's numbers. Faster
for one animation, unreviewable at scale (a binary asset is invisible to the critic — R18's stated
reason). Acceptable for the first prototype; Route A before milestone lock.

**Neither route is verified.** Route A's UMG-animation Python surface is real but fiddly and has
never been run in this repo.

### 1.5 Sequencer display rate — set it to 30 fps

Every measured number in `MOTION-MEASURED.md` is a multiple of **30 ms**, because the reference GIFs
are 30 ms/frame. Set each widget animation's display rate to **30 fps** and every timing snaps to an
integer frame with no rounding:

| measured value | frames @30 fps |
|---|---|
| flicker period 60 ms [M] | **2** — literally the measured "2-frame alternation" |
| stagger 150 ms [M] | **5** |
| expand/collapse 330 ms [M] | **11** |
| reroll narrow 360 ms [M] | **12** |
| banner hold 1590 ms [M] | **53** |

Display rate is an authoring snap only; MovieScene's tick resolution (24000/s) stores the real time
and playback interpolates continuously. Nothing plays at 30 Hz.

### 1.6 What UMG genuinely cannot do here

- **No shared curve token.** There is no "easing asset" a UMG track can reference. The curve is
  duplicated into every track. That is exactly why Route A (generate them) beats Route B (type them)
  — one generator, N tracks, one place to fix the curve.
- **No C++ easing function inside a track.** A track cannot call `UBRUIMotion::EaseStandard()`.
  Anything needing C++-evaluated easing needs a C++ timer driving a property, which is a worse
  design than a track; see §6.1 for how to avoid needing it at all.
- **`UMG Transition` / anim-graph-style blending does not exist.** Interruption is handled by
  playing a second animation, not by blending two.

## 2. The motion vocabulary

Nine named transitions. Every screen and HUD element composes from these; a tenth requires adding it
here first (`ui-presentation` §2's design-system-before-screens rule, applied to motion).

Naming convention for the bound animation: `Anim_<Verb>` on the widget's C++ class.

### 2.1 Structural rules that apply to all of them

Three rules from `MOTION-MEASURED.md` that are structure, not timing, and override any row below:

1. **Animate the fill; snap the frame.** [M] Objective Complete's outer stroke goes 43 px → 278 px
   in **one frame (30 ms)** — a hard cut. Panel borders, rules, and container outlines get a
   **Constant-interp** visibility/size key. Only the fill, the content, and the text ease.
2. **Text reveals are linear.** [M] The VISR type-on is constant-rate across 16 frames:
   **15.6 px/frame ≈ 520 px/s ≈ 42 ms per 22 px glyph**, no easing at either end. A type-on track
   uses **Linear** keys. Easing a text reveal is a defect.
3. **Flicker is a hard toggle, not a fade.** [M] 60 ms period, 16.7 Hz, alternating between two
   discrete states. Implement as **Constant**-interp keys on opacity or a colour switch — never as a
   cubic ramp.

### 2.2 The table

| # | Name | Duration | Curve | Properties animated | UMG track |
|---|---|---|---|---|---|
| 1 | **Screen In** | **330 ms** [M] | Standard | Panel fill `Scale.Y` 0→1 about centre; content `Opacity` 0→1 delayed 60 ms; border visibility snaps at frame 0 | `Anim_ScreenIn` — Transform (Scale) on the fill `SizeBox`; Constant key on the border `Image`; Float track on content `RenderOpacity` |
| 2 | **Screen Out** | **330 ms** [M] | Standard | Exact mirror of Screen In | `Anim_ScreenIn` played **reverse** — [M] "the in and out are the same curve and the same duration… a symmetric transition, not an in/out pair" |
| 3 | **Panel Expand / Collapse** | **330 ms** [M] in *and* out | Standard | `Height` **and** `Y` together, symmetric about the panel's pinned centre; injected rows fade `Opacity` 0→1 over the last 150 ms | `Anim_Expand` — Float track on `SizeBox.HeightOverride` + Transform `Translation.Y` on the panel root |
| 4 | **List Stagger** | **150 ms per beat** [M]; block total = `150 × N` | Standard per item | Per-row `Translation.Y` +12 px→0 [P] and `Opacity` 0→1 | `Anim_RowEnter` on the **row** widget; C++ schedules the offsets — see §7.3 |
| 5 | **Focus Move** | **120 ms** [P] | Standard | Caret (`Rectangle 278`, 3×65, `SCREEN-BUILD-SPEC` §2) `Translation.Y` to the focused row; row text `Opacity` 0.70→1.00 | `Anim_CaretMove` on the list container, retargeted per-play by C++ (§7.4) |
| 6 | **Selection Commit** | **0 ms + 120 ms** [M cadence] | none / Constant | Rule thickness snaps 1px→**2px**, text→**full white** (`ui-presentation` §2) at frame 0; then **2 flicker beats of 60 ms** [M] | `Anim_Commit` — Constant keys only, 4 keys at 0 / 60 / 120 ms |
| 7 | **Error Shake** | **180 ms** [P] | none / Constant | `Translation.X` ±6 px [P] on a 60 ms beat [M cadence], 3 beats | `Anim_Error` — Constant-interp Transform track, 0 / 60 / 120 / 180 ms |
| 8 | **Notification Enter / Hold / Exit** | **330 / 1590 / 330 ms** [M] — 2460 ms total life | Standard in and out | Enter = Screen In on the notification's fill; hold is static; exit = Screen Out | `Anim_NotifyIn`, then a C++ timer, then `Anim_NotifyIn` reversed |
| 9 | **Narrow-In-Place** | **360 ms** [M] | `cubic-bezier(0.30,0.20,0.15,1.00)` [M] — the one row that does **not** use Standard | One edge pinned, the other slides: e.g. Challenge Card 511.5→461.5 while a 40×40 swap button slides in | `Anim_NarrowInPlace` — Float track on left padding |

**Why row 9 keeps its own curve.** [M] The VISR chip's pinned-edge narrow fits `(0.30, 0.20, 0.15,
1.00)` at RMSE 0.009, and it is the exact move `SCREEN-BUILD-SPEC` §7's reroll affordance performs.
It is close enough to Standard that using Standard is defensible; it is measured separately, so it
is recorded separately. Use Standard if the extra track is not worth it — say so in the ticket Log.

### 2.3 Proposals, stated as proposals

| value | why this number |
|---|---|
| Focus Move **120 ms** [P] | Must be strictly **shorter than the 150 ms stagger** [M] so a held D-pad direction never queues caret moves behind each other. 120 ms = 4 frames on the 30 ms grid, the largest value that satisfies that with margin. |
| Row-enter offset **+12 px** [P] | The menu row pitch is 40 with a 12 px gap (`ui-presentation` §5). Travelling exactly the gap makes the motion read as "the row slid out of the one above it". |
| Error Shake **180 ms / ±6 px** [P] | 180 ms is the [M] flicker-phase length in both Objective Complete and Mission Complete; ±6 px is half the row gap, the largest displacement that cannot be mistaken for a layout change. |
| Hover **90 ms** [P] | See §4.4 — hover is folded into focus, so this is colour-only and exists mainly to stop a mouse sweep from strobing. |
| Hold-to-confirm **660 ms** [P] | 2 × the 330 ms house transition [M]. Long enough to be deliberate, short enough not to feel punitive. |

### 2.4 Explicitly not adopted from the reference

- **The Eagle Loader is not a spinner.** [M] It is a 1800 ms one-shot sting that is 13% black by
  duration. Looping it makes the UI go dark once a second. Use it as a **load-screen entry sting**;
  the busy indicator is a separate asset. `SCREEN-BUILD-SPEC` §7's "4-frame Loading Icon" line is
  superseded.
- **The `Searching` / `Searching 2` two-state loop has no measured period.** [M] states plainly that
  the only measured two-state alternation is the 60 ms glitch, which is a damage/impact effect;
  16.7 Hz would strobe a search indicator. **Left open. Do not adopt 60 ms for it.** [P] if a number
  is needed to unblock: **600 ms** per state — an order of magnitude off the glitch so the two read
  as different languages — and re-measure before ship.
- **The VISR progress bar's 4-step timing.** [M] "trailer choreography, not a data-driven bar." A
  real bar is driven by real completion. Only the total transfers: a scripted completion beat reads
  as done in **360 ms**.

## 3. Screen transitions — CommonUI push/pop

### 3.1 The mapping

`UBRUIManagerSubsystem` already owns the layer stack (`Layer.Game` / `Layer.GameMenu` / `Layer.Menu`
/ `Layer.Modal`) and exposes `PushWidgetToLayer` / `RemoveWidgetFromLayer` / `ClearLayer`.
`UCommonActivatableWidget` gives the four lifecycle points motion hangs off:

| CommonUI event | What plays | Notes |
|---|---|---|
| `NativeOnActivated` | **Screen In** (330 ms [M]) | Also the only place delegates bind (`ue5-ui-architecture` §2) |
| `NativeOnDeactivated` | nothing — too late | The widget is already down. See §3.2. |
| Push over an existing screen | the incoming plays Screen In; the outgoing does **not** animate | A stack is not a crossfade — the layer beneath is still there, just covered |
| Pop | **Screen Out** on the popping widget, *then* removal | Requires the deferred-removal pattern in §3.2 |

### 3.2 The one piece CommonUI does not hand you: an exit animation

`RemoveWidgetFromLayer` destroys the widget. If it is called first, Screen Out never renders. The
lawful pattern, entirely in C++ on `UBRActivatableWidget`:

```
// UBRActivatableWidget::RequestDismiss()
//   1. if Anim_ScreenIn is null  -> RemoveWidgetFromLayer immediately (no animation authored)
//   2. else PlayAnimationReverse(Anim_ScreenIn)
//   3. bind UUMGSequencePlayer::OnSequenceFinishedPlaying (a delegate, not a timer, not Tick)
//   4. in the handler -> UIManager->RemoveWidgetFromLayer(...)
```

Guardrails, all of them C++:
- **Input is dead the moment dismissal starts.** Deactivate first, then animate, so a second Back
  press during the 330 ms cannot double-pop.
- **Unbind ViewModel delegates in `NativeOnDeactivated`**, before the exit animation — a leaked
  binding outliving the widget is the crash `ue5-ui-architecture` §2 names.
- If `OnSequenceFinishedPlaying` has not fired within **2 × duration**, remove anyway. A missing
  callback must not strand a screen on the stack.

### 3.3 The unzip origin

`SCREEN-BUILD-SPEC` §2 finds `Rectangle 258` / `Rectangle 259` — 88×4.7 chamfer notches subtracted
from the panel border, top and bottom. **The reveal wipe originates from these, which is why the
reference panel appears to unzip rather than fade.** So Screen In's fill scale is on `Scale.Y` about
the panel's vertical centre, not a uniform scale and not an opacity fade. Duration is measured
(330 ms); the notch origin is structural, from the geometry.

### 3.4 The two-state frame

`SCREEN-BUILD-SPEC` §2: the list↔grid swap is **one WBP with a state switch**, not two screens. So
it is not a push/pop at all — it is a `UWidgetSwitcher` index change with **Panel Expand/Collapse**
(330 ms [M]) on the outgoing state and 330 ms on the incoming, sequenced by C++:

```
Collapse(list) 0-330ms  ->  switcher index change (1 frame)  ->  Expand(grid) 330-660ms
```

660 ms total. [P] on the sequencing — the reference has no measured list↔grid swap. The *individual*
330 ms halves are measured; the decision to sequence rather than crossfade is design, and it is
chosen because [M]'s frame-snap rule says these panels do not fade.

### 3.5 What plays when — the front-end flow

| Transition | Motion |
|---|---|
| Boot → Main Menu | Eagle-class **load sting once** (1800 ms [M]), then Screen In |
| Main Menu → Customize (same chrome) | **no screen transition** — `SCREEN-BUILD-SPEC` §3: "the 3D subject does not re-frame". Only the Menu Combo's rows restagger (150 ms [M] × N) |
| Any level → drill-down (title band 75↔105, nav y 45→75/110) | Title band **snaps** [M frame rule]; content below shifts 40 px with Panel Expand's curve over 330 ms [M] |
| Filter Page / Pop-Up Options (`Layer.Modal`) | Scrim `Opacity` 0→1 over 330 ms [M]; panel Screen In. Not a navigation level — the layer beneath is untouched |
| Match found → HUD | Screen Out on the menu layer, `ClearLayer(Layer.Menu)`, `ShowHUD`. **The HUD does not play Screen In** — see §6.0 |
| Death → death overlay (`Layer.GameMenu`) | Screen In 330 ms [M] |

## 4. Focus and selection — gamepad and KBM parity

### 4.1 CommonUI does the navigation; we do not

`ue5-ui-architecture` §6 is unambiguous: "hand-rolled focus math is a finding." Concretely:
- `UCommonActivatableWidget::GetDesiredFocusTarget()` — override in C++, returns the widget that
  takes focus on activation. Every screen overrides it. A screen that activates with nothing focused
  is unusable on a controller and is a finding.
- Directional travel is Slate's navigation system, driven by CommonUI's analog/D-pad input.
- Back is the activatable stack popping. Not a bespoke handler.

### 4.2 Wrap behaviour — set it in C++, not the details panel

Vertical wrap on menu lists, no horizontal wrap on tab strips (LB/RB is the horizontal axis and it
already wraps — see §5.4). Set with `SetNavigationRuleBase(EUINavigation::Up/Down,
EUINavigationRule::Wrap)` in `NativeOnInitialized`.

**Why C++ and not the WBP's Navigation details panel:** wrap-vs-stop is behaviour, and
`ui-presentation` §8 puts behaviour on the code side of the boundary. A navigation rule set in a
binary asset is a decision the critic cannot diff.

**Grids wrap in one axis only.** The 4-column item grid (`SCREEN-BUILD-SPEC` §1: tile 114, pitch
130, origin 86,260) wraps vertically; horizontal Right from column 4 **stops**, it does not jump to
column 1 of the next row. Column-1↔column-4 teleporting is disorienting on a stick. [P] — the
reference does not show grid navigation.

### 4.3 The three states, and their treatment

| State | Treatment | Motion |
|---|---|---|
| **Rest** | 1px rule, text at 70% white [P on the 70%] | — |
| **Focused** | Caret (3×65 at x=−4) at this row; text 100% white | **Focus Move**, 120 ms [P] |
| **Selected / committed** | **2px rule + full white** (`ui-presentation` §2) | **Selection Commit** — snap + 2 × 60 ms flicker [M cadence] |
| **Disabled** | text 35% white [P], no caret, skipped by navigation | — |

The caret is **one instance that moves**, not one per row. `SCREEN-BUILD-SPEC` §2 found its authored
y values encode the focus index (54 / 78 / 98 / 138 / 180) — the design already assumes a single
travelling caret. Same reasoning as the Forge thumbstick indicator ("one indicator rotated in 90°
steps, not four assets").

### 4.4 Hover vs focus — resolved by merging them

**Hover takes focus.** A mouse entering a row sets focus on that row; the caret moves there with the
same 120 ms Focus Move; there is no separate hover treatment beyond the cursor.

Reason: any design where hover and focus are different states can show **two "current" rows** at
once — mouse hovering row 3 while the gamepad caret sits on row 1. The player then does not know
what Enter/A will activate. Merging them makes gamepad/KBM parity structural instead of something
that has to be tested for. It also deletes a state, a treatment, and an animation.

Cost, stated: mouse-users lose "preview by hovering without committing focus". For a 4v4 arena
shooter's front end that is not a real loss. If a screen ever genuinely needs it, it comes back
here as a tenth vocabulary entry before it is built.

The 90 ms [P] hover fade survives only as the *colour* transition on the row text so a fast mouse
sweep across eight rows does not strobe.

### 4.5 Parity requirements

- Every path is reachable with **no mouse plugged in**: menu → match → death → rematch
  (`ue5-ui-architecture` §6, the M6 stranger test).
- Every path is reachable with **no controller**: the caret responds to arrows/Tab identically.
- Prompt glyphs match the device currently in use (§5.2), and they swap on the device that produced
  the **last input**, not the last device connected.

## 5. Input

> **API-drift warning.** `ue5-ui-architecture` carries a standing UNVERIFIED-DRAFT notice: CommonUI's
> activation and input-routing surface has moved across UE 5.x, and these are exactly the details
> that are either right or a compile error. Treat §5 as *the intent*, and correct the specifics in
> the first packet that builds against 5.8 — with the delta written into the ticket Log.

### 5.1 Actions, never keys

`ue5-ui-architecture` §6: "The UI never binds a raw key." Input reaches widgets as CommonUI input
actions (`FDataTableRowHandle` into the Common Input Action data table), routed through the same
`BRInputConfig` tags the ASC uses.

| Action | Bound where | Motion consequence |
|---|---|---|
| `UI.Confirm` | focused row | **Selection Commit**, then whatever the commit does |
| `UI.Back` | the activatable widget | §3.2 dismissal — Screen Out, then pop |
| `UI.TabLeft` / `UI.TabRight` | the nav bar (`UBRNavBar`) | §5.4 |
| `UI.Reroll` (hold) | Challenge Card | §5.3 |

### 5.2 Glyph swap on device change

`UBRButtonPrompt` (component inventory, `ui-presentation` §2) wraps a `UCommonActionWidget` bound to
an input-action row. CommonUI resolves the glyph for the **current input method** automatically —
gamepad face button, keyboard key cap, touch — and re-resolves it when the method changes. We supply
the action row and the brush set, not the swap logic.

For anything CommonUI does not cover on its own, `UCommonInputSubsystem::OnInputMethodChangedNative`
is the delegate to hook. **It is a delegate — law 4 is satisfied; nothing polls
`GetCurrentInputType()` per frame.**

Layout consequence: `SCREEN-BUILD-SPEC` §1 measures the prompt bar's width tracking the prompt
**count** (58/62 for 1 · 133/146 for 2 · 253 for 3), and §7 says it must be auto-layout hug. In UMG
that is a `HorizontalBox` with `Auto` slot sizing inside a right- or left-aligned container —
**never** a fixed-width `SizeBox`. A glyph swap can change a prompt's width (a keyboard "SPACE" cap
is far wider than an "A" button), so the bar must reflow. **The reflow does not animate** [M frame
rule: chrome snaps].

### 5.3 Hold-to-confirm

For destructive or costly actions (Reroll, Leave Match, Reset to Default). CommonUI's action
binding supports a hold variant with a progress delegate (`FBindUIActionArgs`' hold fields; exact
member names to be confirmed against 5.8).

- **Duration: 660 ms [P]** — 2 × the house 330 ms [M].
- **The ring fills linearly.** Not eased. A progress indicator is a data readout, and [M]'s type-on
  finding is the same principle: a constant-rate reveal must not be eased. A hold ring that eases
  lies about how much longer the player must hold.
- **Release before completion cancels**, and the ring empties over **165 ms** [P] (half the fill) —
  fast enough to read as abandoned, not as a second animation.
- On completion: **Selection Commit** (§2 row 6).

Driving it: the progress delegate is a CommonUI callback, not a Tick. The ring's value binds to a
C++-held float updated in that callback. **This is the one place a per-frame-ish callback is
lawful** — it is CommonUI's, invoked while the button is held, and it ends when the hold ends. It is
not `NativeTick` and not a UMG property binding.

### 5.4 Bumper / Tab routing

`UBRNavBar` is a `UCommonTabListWidgetBase` (or holds one) with `SetLinkedSwitcher(...)` pointing at
the screen's `UWidgetSwitcher`. LB/RB (gamepad) and Q/E or Shift+Tab/Tab (KBM) map to
`UI.TabLeft` / `UI.TabRight`, which call `SelectPreviousTab()` / `SelectNextTab()`.

- **Tabs wrap horizontally** — last→first. A four-tab strip is short enough that wrapping is faster
  than backtracking. [P].
- Tab switch plays **Panel Expand/Collapse's curve at 330 ms** [M] on the switcher's content, with
  the tab strip's own underline sliding via **Focus Move** (120 ms [P]).
- The bumper glyphs flanking the 284×36 rail (`SCREEN-BUILD-SPEC` §5, "Bumper Tab Strip") are
  `UBRButtonPrompt` instances and swap per §5.2 — on KBM they become the key caps, they do not
  disappear.

## 6. HUD motion

`ui-presentation` §4: *"minimal and flat when far from play; the VISR colour philosophy and more
skeuomorphic treatment once in-game."* And its consequence: **"if the HUD's shield bar and the
lobby's progress bar look identical, one of them is wrong."** So the HUD gets glow, segmentation,
state colour, and motion the menus are not allowed. It also gets a harder rule the menus do not:

> **§6.0 — HUD motion never delays information.** The HUD does not play Screen In on match start; it
> is simply there. A value that changes changes **now**; only its *decoration* eases. A shield bar
> that takes 330 ms to show that you have been shot has lied to the player for 330 ms. Every row
> below is written so the number is instant and the flourish is what animates.

### 6.1 Shield / health response

`ui-presentation` §3 colour law: `--shield #35D0F2` means **you**; `--health #F5C542` appears **only
after damage**; health is yellow, never green. `--enemy #FF4A3D` is the shield-break flash.

| Sub-element | Motion | Feed |
|---|---|---|
| **Shield fill (damage)** | **Instant.** Zero interpolation. | `ShieldPercent` FieldNotify — **exists** |
| **Shield chip trail** | A second bar behind the fill, at the *previous* value, catching up over **330 ms** [M] on Standard, after a **240 ms** [P] delay | Same FieldNotify; the trail is a UMG track, not a second field |
| **Shield refill** | Follows the attribute as it regenerates — the GE drives the rate, the bar does not smooth it | `ShieldPercent` FieldNotify |
| **Shield break** | 2 × 60 ms flicker [M] in `--enemy`, then the health bar becomes visible (snap) | `ShieldsBrokenEvent` (`FMVVMEventField`) — **exists** |
| **Shield restored** | Health bar hides after a **330 ms** [M] fade | `ShieldsRestoredEvent` — **exists** |
| **Health fill** | Instant, same rule as shields | `HealthPercent` FieldNotify — **exists** |

**Why the chip trail instead of lerping the bar.** It gives damage-magnitude feedback *without* any
C++ interpolation, any timer, or any lie about the current value. The live bar is truth; the trail
is a UMG animation played once per hit. This is the design that makes `ue5-ui-architecture` §3's
"presentation smoothing lives on the ViewModel" mostly unnecessary — and the smoothing that would
have lived there was the part that risked feeding back into the sim.

### 6.4 Killfeed enter / exit

The pool already exists (`FUserWidgetPool KillfeedPool` in `BRHUDLayout.h`), and
`ue5-ui-architecture` §5's rule stands: entries are claimed and released, never
`CreateWidget`/`RemoveFromParent` per kill.

| | |
|---|---|
| Enter | **150 ms** [M — one stagger beat], `Translation.X` −24 px→0 [P] + `Opacity` 0→1, Standard |
| Existing rows shifting down | The same 150 ms [M], same curve, same frame — this is the [M] stagger cadence applied spatially |
| Exit | Fade **240 ms** [P — shorter than enter; a departing row must not compete with an arriving one] at `KillfeedEntryLifetimeSeconds` (6.0 s, already in `UBRUISettings`) |
| Local-player rows | White (`#FFFFFF` — `ui-presentation` §3: "you, in a list of people"), plus 1 × 60 ms flicker [M] on enter. Enemy team rows `--team-them #FF7A45` |
| Spotter line | Reserves its slot always; renders empty when the string is empty; **never animates on arrival**. It appends late (LLM), and an animation firing 2 s after the kill draws the eye back to old information |
| Feed | `OnKillfeedEntryAdded` (new entry) and `OnKillfeedChanged` (expiry) — **both exist** |

> **Finding against the current C++.** `UBRHUDLayout::HandleKillfeedChanged()` calls
> `RebuildKillfeed()`, which reconstructs every row. With enter animations attached, **every row
> replays its enter animation on every kill.** The fix is in C++, not the asset: diff by
> `SequenceId` and play `Anim_RowEnter` only on rows whose `SequenceId` was not present before.
> Filed here; not fixed here (this packet writes one file).

### 6.6 The C++ gaps this spec creates

`ui-presentation` §8: *"If a field does not exist on a ViewModel, that is a C++ gap — file it, do not
work around it in the widget."* Two, both on `UBRVM_Combat`:

| Gap | Needed shape | Fed by |
|---|---|---|
| **Damage direction** | `FMVVMEventField DamageTaken` + `float GetLastDamageYaw()`, plus `ReportDamageTaken(float YawDegrees)` | The damage GameplayCue handler (C++ class) on the receiving client |
| **Medal award** | `FMVVMEventField MedalAwarded` + `FGameplayTag GetLastMedalTag()`, plus `ReportMedal(FGameplayTag)` | The medal GameplayCue handler |

Both follow the existing hit-marker pattern exactly (`ReportHitMarker` → `FMVVMEventField`), so they
are additive and cheap. Neither is written here.

**Also a gap, on the HUD layout rather than a ViewModel:** `BRHUDLayout.h` currently exposes its
reactions as `BlueprintImplementableEvent` (`BP_OnShieldHit`, `BP_OnFleshHit`, `BP_OnKillConfirmed`,
`BP_OnVitalsStateChanged`, `BP_OnMatchStateChanged`, `BP_OnKillfeedRebuilt`). **Implementing any of
them requires graph nodes in the WBP, which fails R26 condition 2 and is a `high` finding.** The
replacement is one-for-one and simpler: a `BindWidgetAnim` pointer per reaction, played from the
existing C++ handler. The `BlueprintImplementableEvent` declarations should be removed in the same
packet that authors the first HUD animation.

### 6.7 Join-in-progress: what plays on an unknown value

`ue5-ui-architecture` §7 and `EBRUIDataState::Unknown`. **Unknown does not animate.** A widget in
`Unknown` renders dashes or a dimmed plate and plays nothing. The transition Unknown → Live plays
**Screen In** (330 ms [M]) on that element only — so the first real data arrives with a deliberate
reveal instead of a value silently mutating from `--` to `100`. `Live → Stale` dims over 330 ms [M];
`Stale → Live` restores instantly (§6.0: information is never delayed).

## 7. What drives each animation

**The rule, restated:** every animation is `PlayAnimation()` called from C++, from a delegate
handler. No `NativeTick`. No UMG property binding (`ue5-ui-architecture` §8 calls that "the
per-frame poll wearing a different hat"). No widget graph node.

### 7.1 The trigger table

| Animation | C++ trigger | Delegate source |
|---|---|---|
| Screen In | `UBRActivatableWidget::NativeOnActivated` | CommonUI lifecycle |
| Screen Out | `UBRActivatableWidget::RequestDismiss` → `UUMGSequencePlayer::OnSequenceFinishedPlaying` → `RemoveWidgetFromLayer` | CommonUI + MovieScene player delegate |
| Panel Expand/Collapse | The C++ handler for the row's `UI.Confirm` action binding | CommonUI action binding |
| List Stagger | `UBRMenuList::PopulateRows()` → §7.3 | C++ call, populated from data |
| Focus Move | `UWidget::OnFocusReceived` / CommonUI's focus-changed callback on the row → container's `MoveCaretTo(Index)` | Slate focus event |
| Selection Commit | The row's `UI.Confirm` handler | CommonUI action binding |
| Error Shake | The C++ handler that rejected the action | Direct call at the rejection site |
| Notification Enter/Exit | `UBRVM_Match` field-changed handler; exit by `FTimerHandle` after 1590 ms [M] | `FieldNotify` + `FTimerManager` |
| Narrow-In-Place | The Challenge Card's focus-received handler | Slate focus event |
| Hit markers | `UBRVM_Combat::OnHitMarker()` broadcast, already handled by `UBRHUDLayout::HandleHitMarker` | `FBROnHitMarker` multicast |
| Shield chip trail | `HandleViewModelFieldChanged` on `ShieldPercent` | `FieldNotify` |
| Shield break / restore | `ShieldsBrokenEvent` / `ShieldsRestoredEvent` | `FMVVMEventField` |
| Damage direction | `DamageTaken` event field — **gap, §6.6** | GameplayCue handler → ViewModel |
| Medal | `MedalAwarded` event field — **gap, §6.6** | GameplayCue handler → ViewModel |
| Killfeed row enter | `UBRVM_Match::OnKillfeedEntryAdded()` | `FBROnKillfeedEntryAdded` multicast |
| Killfeed row exit | `OnKillfeedChanged` after the VM's expiry timer | `FBROnKillfeedChanged` + `FTimerManager` |
| Hold-to-confirm ring | CommonUI's hold-progress delegate | CommonUI action binding |
| Prompt glyph swap | `UCommonInputSubsystem::OnInputMethodChangedNative` | CommonUI delegate |
| Load sting | `NativeOnActivated` of the load screen, once | CommonUI lifecycle |
| Scanlines | Material `Time` node | Not a widget animation at all |

Every entry is a lifecycle hook, a delegate, or a timer. That is the whole list of lawful sources
under law 4, and nothing here needs anything else.

### 7.2 Timers, not Tick, for held phases

The 1590 ms notification hold [M] and the 6.0 s killfeed lifetime are `FTimerManager` handles.
`UBRVM_Match` already does exactly this (`ClockTimerHandle`, `KillfeedExpiryTimerHandle`,
`ScheduleNextClockUpdate`) — the pattern is established, follow it. Cancel every handle in
`NativeOnDeactivated` / `BeginDestroy`.

### 7.3 Stagger without a Tick and without N timers

The 150 ms [M] stagger has an exact UMG solution that costs zero timers:

**`PlayAnimation(Anim, StartAtTime, NumLoops, Mode, Speed)` accepts a start time.** Author each row's
`Anim_RowEnter` with **150 ms of dead space per index prepended** — no. Simpler and lazier: play the
*same* animation on every row in the same frame, and give row `i` a **negative start offset** by
authoring the animation with a leading hold and calling
`PlayAnimation(Anim_RowEnter, /*StartAt=*/ 0.0f)` on row 0, row 1, … after `i × 150 ms`.

The cheapest correct version, and the one to build:

```
// UBRMenuList::PopulateRows()  — one timer for the whole list, not one per row
//   StaggerIndex = 0
//   PlayRowEnter(0)
//   SetTimer(StaggerHandle, this, &PlayNextRow, 0.150f, /*bLoop=*/ true)
//   PlayNextRow(): PlayRowEnter(++StaggerIndex); if last -> ClearTimer(StaggerHandle)
```

One looping timer at 150 ms, cleared when the list is exhausted. Not Tick, not N timers, and the
150 ms interval is the measured number itself rather than a derived offset.

[M] the block total for 3 items is 450 ms. For a 6-row Menu Combo (`SCREEN-BUILD-SPEC` §3) that is
750 ms, which is long. **Cap the stagger at 4 beats** [P]: rows 5+ enter with row 4. Total 600 ms.

### 7.4 Retargeting one animation — the caret

Focus Move animates one caret to N possible positions, and authoring N animations is wrong. Author
**one** `Anim_CaretMove` as a 0→1 normalised `Translation.Y` on the Standard curve, and have C++ set
the from/to as a `UMG` transform *offset* on the caret's parent before playing. Where a normalised
track cannot express it, the fallback is a Float track on a `UPROPERTY` the caret's slot reads —
still zero graph nodes, still one asset.

Same pattern for the Forge thumbstick indicator (`SCREEN-BUILD-SPEC` §4: "one indicator rotated in
90° steps, not four assets") and the material-picker accordion (§4: "animate height and y together"
about the pinned y=360 centre).

## 8. Performance budget

**Everything in this section is a proposal.** No Slate profile has been taken for this project. The
numbers are starting caps to be replaced by measurement, and §9 says how.

### 8.1 What a running animation costs

An active `UWidgetAnimation` runs a `UUMGSequencePlayer` that evaluates its MovieScene tracks and
writes properties each frame. Cost is per-track-per-frame, not per-widget, so a 4-track animation on
one widget costs roughly what 4 single-track animations cost. The larger cost is usually the
**invalidation** the property write causes, not the evaluation.

### 8.2 Proposed caps

| Context | Concurrent animations | Reason |
|---|---|---|
| In-match HUD | **12** [P] | 4 damage indicators + 5 killfeed rows + 1 medal + hit marker + chip trail = 12. That is the worst realistic frame, so it is the cap. |
| Front-end screen | **8** [P] | Stagger cap of 4 (§7.3) + screen transition + caret + 2 spare |
| Modal over a screen | **+2** [P] | Scrim + panel. The layer beneath must have finished animating before a modal pushes |
| Absolute ceiling, any frame | **16** [P] | Beyond this, drop the lowest-priority class (§8.4) |

### 8.3 Invalidation discipline — the thing that actually costs frames

A `Retainer Box` or `Invalidation Box` caches its subtree. **An animating child invalidates that
cache every frame**, which is strictly worse than not caching at all.

- **HUD chrome that never moves** (frame plates, static labels, the scanline overlay) goes inside a
  Retainer Box.
- **Everything animating** — killfeed, medals, hit markers, damage indicators, the chip trail —
  goes **outside** it, or inside its own separate boundary.
- Never place an animating widget inside a retainer shared with static content. This is the single
  highest-leverage HUD performance decision and it is a layout choice, so it is authored in the WBP
  and must be checked at review.

### 8.4 The ones that are not safe, and what to do

| Problem | Mitigation |
|---|---|
| **The 16.7 Hz flicker** [M] is a hard 2-frame toggle. At 60 fps it is exactly 2 render frames on / 2 off. **Below 60 fps it aliases**, and at 30 fps it can sample the same phase every frame and vanish entirely | Make it **time-based** (an animation track on wall clock), never frame-counted. **Cap every flicker at 3 toggles / 180 ms** [M — that is the measured phase length]. A flicker nobody sees is a cosmetic loss; a flicker that strobes is an accessibility problem. Provide a **Reduce Flashing** setting that replaces every flicker with a single 60 ms opacity dip |
| **Killfeed spam** — a team wipe pushes 4 entries in under a second, each with an enter animation and each shifting the rows below | The pool already caps at `KillfeedMaxVisibleEntries` (5). Additionally: if a second entry arrives while the first's 150 ms enter is running, **snap the first to complete** and start the second. Never queue killfeed animations — a killfeed running 600 ms behind the fight is worse than one that jumps |
| **Medal queue** at depth 3 = 6.8 s of animation | §6.3's shortened hold; hard queue cap of 3 with logged drops |
| **Stagger on a long list** | §7.3's 4-beat cap |
| **Screen transition overlapping a modal push** | The C++ push path refuses a modal push while the layer beneath has a sequence player running; it defers to `OnSequenceFinishedPlaying`. Two 330 ms transitions running against each other is the classic "the menu ate my input" bug |

### 8.5 Scalability

Motion is one of the first things a low-spec preset should shed. [P] tiers:

| Tier | Behaviour |
|---|---|
| High | Everything in this document |
| Medium | Flicker → single dip; chip trail off; stagger → all rows at once |
| Low | All decorative motion off. **Screen In/Out, Focus Move and Selection Commit stay** — they are navigation feedback, not decoration, and removing them makes the UI feel broken rather than fast |

The tier is read from settings in C++ and gates the `PlayAnimation` call. It is never a branch in an
asset.
